# ENET 阶段一：已有基础复用与源码阅读方法学习讲义

> 对应[项目学习规划的阶段一](项目学习规划.md#stage-1)。按需查阅，不设统一课时。
>
> C++ 和 Linux socket/epoll 的已有知识直接用于项目；遇到具体疑问时，先把问题缩小，再沿调用、数据和对象关系找到答案。没有当前疑问时，可以直接进入[阶段二](项目学习规划.md#stage-2)。

## 1. 从一个具体问题开始

阅读源码时，先明确自己要解释哪一个行为。例如：

- 调用 `SetReadCallback()` 时，会立即执行传入的回调，还是只保存它？
- `OnAccept()` 里的 `fd` 来自哪里，接下来交给谁？
- 回调捕获的 `this` 指向哪个对象，由谁保证它还活着？

问题落到函数、字段或某次行为上，就容易确定阅读范围。先用编辑器的“转到定义”和“查找引用”找到相关位置，再沿当前问题展开；遇到协议解析等无关分支，等对应阶段再读。

熟悉的语法和 API 直接使用。只有说不清某个语言机制或 API 含义时，才查定义或用短片段确认；若含义已知，就继续查本项目如何传参、保存和调用。

## 2. 示例：读回调在哪里保存，何时执行

本例只追踪“监听 socket 的读回调”，使用以下文件：

- [Acceptor.cpp](../EdoyunNet/Acceptor.cpp)：注册回调、接入连接。
- [Channel.h](../EdoyunNet/Channel.h)：保存和调用回调。
- [Acceptor.h](../EdoyunNet/Acceptor.h)：核对成员类型和持有关系。
- [TcpServer.cpp](../EdoyunNet/TcpServer.cpp)：需要继续确认新连接回调的去向时再读。

### 2.1 找到注册位置

`Acceptor::Listen()` 在绑定、监听成功后执行：

```cpp
channelPtr_->SetReadCallback([this]() { this->OnAccept(); });
channelPtr_->EnableReading();
loop_->UpdateChannel(channelPtr_);
```

三行代码分别设置读回调、关注读事件、提交 Channel。这里的 lambda 保存了“以后调用 `OnAccept()`”的动作；传入 lambda 时没有执行它的函数体。

本例先把 `UpdateChannel()` 理解为更新 Channel 事件监听设置的接口。它具体怎样调用 epoll，在[阶段三](项目学习规划.md#stage-3)继续阅读。

### 2.2 看 SetReadCallback 实际做了什么

跳到 `Channel::SetReadCallback()`：

```cpp
inline void SetReadCallback(EventCallback const& cb)
{
    read_callback_ = cb;
}
```

`EventCallback` 是 `std::function<void()>`。这里把传入的可调用对象复制到成员 `read_callback_` 中，并非保存参数 `cb` 的引用。因此，调用结束后，Channel 仍保存着这份回调。

再看 `EnableReading()`：它给关注事件添加 `EVENT_IN` 标志。设置关注标志与收到事件是两个动作。

### 2.3 找到回调的调用位置

查找 `read_callback_` 的使用位置，可以在 `Channel::HandleEvent()` 中找到：

```cpp
if (events & (EVENT_PRI | EVENT_IN))
{
    read_callback_();
}
```

至此，已经能区分两个时刻：

```text
注册时：
Acceptor::Listen
  → Channel::SetReadCallback
  → 保存 lambda

收到对应事件并分发时：
Channel::HandleEvent
  → read_callback_()
  → lambda
  → Acceptor::OnAccept()
```

回调在调用 `HandleEvent()` 的线程中同步执行；`std::function` 和 lambda 本身不会另建线程。项目怎样选择调度线程，在阶段三继续阅读。

### 2.4 跟踪新连接 fd 的传递

接着看 `Acceptor::OnAccept()`：

```text
tcp_socket_->Accept()
  → 得到新连接 fd
  → fd > 0 且 new_connectCb_ 已设置时
  → new_connectCb_(fd)
```

这里的 `fd` 是新接入连接的描述符，与监听 socket 的描述符用途不同。`new_connectCb_` 则是另一份回调，由 `TcpServer` 构造函数注册，用来把新连接交给上层处理。

这条路径说明：读回调先被保存，事件分发时才调用，新连接的 fd 再通过另一份回调交给上层。连接读写在[阶段四](项目学习规划.md#stage-4)学习，业务消息处理在对应的业务阶段学习。

### 2.5 顺手确认对象关系

沿着刚才几处代码，核对三个关系即可：

| 代码位置 | 能确定的关系 |
| --- | --- |
| `TcpServer::acceptor_` | `unique_ptr<Acceptor>` 持有 Acceptor |
| `Acceptor::channelPtr_` | `shared_ptr<Channel>` 持有 Channel |
| `Channel::read_callback_` 中的 `[this]` | 保存 Acceptor 的对象指针，不延长 Acceptor 的寿命 |

因此，Channel 被持有，并不能单独证明 lambda 捕获的 Acceptor 始终有效。先认清这条关系；关闭时怎样撤销回调、释放资源，在[阶段十一](项目学习规划.md#stage-11)集中检查。

## 3. 需要时怎样核对

源码可以直接确定成员赋值、条件分支和调用关系。例如，本例能确定“`SetReadCallback()` 保存回调”“满足读事件条件时调用回调”。

服务是否实际接到连接、fd 的具体值以及回调所在的线程 ID，需要运行程序才能观察。`Start()` 返回成功或日志打印 success，也不能证明连接接入和业务处理均已成功。

根据当前疑问，选择一种核对办法即可：

| 当前疑问 | 合适的办法 |
| --- | --- |
| 某条路径是否执行，参数是什么 | 查看已有日志，或在相关位置设断点 |
| 谁调用了当前函数 | 在断点处查看调用栈 |
| 回调实际在哪个线程执行 | 在回调断点处查看线程 |
| 某个 C++ 机制仍不清楚 | 用熟悉代码或一个短片段确认该机制 |

运行前按[阶段零](阶段00_工程与构建基线学习讲义.md)的说明核对环境与监听地址。服务已具备运行条件时，可以在注册回调的位置和 `Acceptor::OnAccept()` 分别设断点，再发起一次 TCP 连接，比较两个断点的触发时机。通过日志或断点回答了当前问题后，就继续阅读。

若服务尚未运行，仍可先手推 `HandleEvent()` 收到 `EVENT_IN` 时的分支；将“源码推演”与“实际观察”分清即可。

## 4. 有实际缺口时再补基础

先区分自己卡在哪里，再选择下一步：

| 卡点 | 下一步 |
| --- | --- |
| 不清楚某个语法、类型或 API 的含义 | 查声明、文档或用短片段确认，然后回到原函数 |
| 知道 API，但不清楚本项目为何这样用 | 继续查调用方、成员赋值和使用位置 |
| 缺少当前主题的理论基础 | 到首次使用它的阶段先补概念并对照现成示例代码，再读项目实现；需要验证理解时，按该阶段安排运行或小改示例 |
| 工具、依赖或监听条件阻断运行 | 回阶段零定位环境问题，先推进不依赖运行的源码阅读 |
| 当前实现与预期行为不一致 | 结合条件和返回值定位；原因已理解、且只需小幅修改就能解除阻断时，可做最小修复，否则记下未解点 |

各主题的基础学习位置如下：协议布局在[阶段二](项目学习规划.md#stage-2)，线程与调度在[阶段三](项目学习规划.md#stage-3)，定时器在[阶段五](项目学习规划.md#stage-5)，数据库在[阶段六](项目学习规划.md#stage-6)，RTMP 在[阶段八](项目学习规划.md#stage-8)。客户端的基础按客户端规划补学。

当你能围绕当前问题找到相关函数，解释关键调用、数据或对象关系，并知道尚需怎样核对时，就继续原阶段。
