## 2. 先补清四个概念

### 2.1 原子标志解决单次访问，不代替退出协议

两个线程无同步地访问同一个普通成员，至少一方写入时，可能形成数据竞争。判断依据是实际访问与同步关系，不是有没有 sleep，也不是机器上暂时有没有复现异常。

`std::atomic_bool` 可以保证对该标志本身的原子读写，但还要分别判断：

- 谁允许启动、停止和再次启动，停止请求会不会被后来的写入覆盖。
- 线程当前是否困在回调、锁或阻塞操作中，能否再次检查标志。
- 与标志有关的其他成员及对象寿命，是否有各自的同步与持有依据。

本项目的 `is_shutdown_` 已经是 atomic；它仍存在第 8 节的启动与停止时序缺口。把其他 bool 改成 atomic，也不能自动解决连接被提前释放或锁顺序相反的问题。

### 2.2 锁保护的是约定的访问范围

一把 mutex 只有在相关读写都遵守同一同步约定时，才能保护共享数据。某个类中声明了 mutex，或某个方法局部加锁，不代表整个对象已经线程安全。

还要区分两类等待：

- **同线程重入**：持有普通 mutex 的方法同步调用回调，回调又请求同一把锁，可能把自己阻塞。
- **跨线程锁顺序相反**：线程甲拿着锁 A 等 B，线程乙拿着锁 B 等 A，形成相互等待。

先沿真实调用链找到第二次取锁，再判断能否同时发生。第 7 节使用项目里的服务锁、会话锁和连接锁说明，不要求另写死锁演示。

### 2.3 持有对象与保护对象内容是两回事

| 方式 | 能提供什么 | 仍需检查什么 |
| --- | --- | --- |
| 局部 shared_ptr | 在该局部持有期间保留对象 | 对象成员是否允许并发访问，局部指针何时销毁 |
| weak_ptr::lock | 成功时取得本次使用的强引用 | 取得后仍需相应同步；逻辑关闭不一定使 weak_ptr 失效 |
| 裸指针、`[this]` | 保存地址，供以后调用 | 不延长对象寿命，调用前必须另有存活保证 |
| 容器中的 shared_ptr | 容器保留该对象 | 从容器移除后还有谁持有，当前回调栈是否仍使用它 |

shared_ptr 的引用计数不会替被指向对象的字段加锁。不同线程各自持有独立的 shared_ptr 副本时，控制块的引用计数可以安全地并发维护；但同一个 shared_ptr 成员若一边被 reset、一边被读取，仍需同步。引用计数安全、指针变量的访问安全与对象字段的访问安全，需要分别判断。

从表中移除、逻辑 Close 和析构是三个时刻，可能相隔很久，也可能在同一条回调栈中紧接着发生。

### 2.4 请求停止、等待结束与释放资源各有条件

`TaskScheduler::Stop()` 只发出停止请求；线程需要返回到检查点后才能结束。`join()` 成功返回，才确认被等待线程已经结束，并使其完成与等待方后续执行建立同步关系。join 不会主动终止线程，也不会修复运行期间已经发生的数据竞争。

等待时不能持有目标线程退出所需的锁，也不能在工作线程中 join 它自己。`joinable()` 表示线程对象仍有关联的可等待线程，不等于线程函数当前还在运行。

同样，释放最后一个 shared_ptr 不会自动等待裸回调结束。资源必须保留到最后一个使用者停止访问；清理所需的调度器也必须活到注销等操作完成。

## 3. 当前线程与关键共享状态

### 3.1 先确定执行位置

`EventLoop` 构造函数立即调用 Loop，创建调度器并启动工作线程。当前几个入口为：

| 服务入口 | 调度线程数 | 主要执行位置 |
| --- | --- | --- |
| [LoadBanceServer/main.cpp](../LoadBanceServer/main.cpp) | 1 | 监听、连接事件和相应业务回调在同一工作线程 |
| [LoginServer/main.cpp](../LoginServer/main.cpp) | 1 | 登录业务与 0 号定时器；主线程仍参与构造、启动和析构 |
| [SigServer/main.cpp](../SigServer/main.cpp) | 1 | 信令连接事件在同一工作线程；主线程退出可与它交错 |
| [RtmpServer/main.cpp](../RtmpServer/main.cpp) | 2 | 监听与服务级定时器在 0 号；接入连接按选择结果分配给调度器 |

EventLoop::UpdateChannel 和 EventLoop::AddTimer 固定转交 0 号调度器；连接内部直接使用自己的 TaskScheduler。不能把这两种定时器注册入口混为一谈。

更关键的是：`Send()` 没有自动投递到连接所属线程。它在调用线程入队后立即调用 HandleWrite。因此发布连接在分发媒体时，可以在发布线程中写另一条播放连接；写失败引发的 Close 与业务关闭回调，也会沿当前调用栈执行。

### 3.2 用读写位置判断保护范围

| 状态 | 当前访问与保护 | 本阶段应得出的判断 |
| --- | --- | --- |
| TaskScheduler::is_shutdown_ | Start、Stop 与循环条件使用 atomic | 单次读写受保护，启动重置和退出依赖仍要检查 |
| EventLoop::index_ | GetTaskSchduler 中普通读写，无锁 | 当前接入路径在监听线程串行选择；若另有线程调用该方法，才需要补相应同步 |
| TcpServer::connects_ | 接入时添加、关闭回调移除、Stop 遍历，无容器锁 | 多调度器和主线程退出均可能交错；Stop 还存在同步删除当前元素的问题 |
| TcpConnection::is_closed_ | Close 中写入；Send、HandleWrite、IsClosed 有锁外读取 | 连接 mutex 没覆盖所有读写，跨线程调用时缺少统一同步 |
| 连接读写缓冲 | recv 与写队列操作局部持连接锁；业务解析在读锁释放后执行 | 局部缓冲锁不保护派生类的全部协议状态 |
| EpollTaskScheduler::channels_ | 添加、修改、移除持调度器 mutex；分派直接用裸 Channel* | 表项更新有锁，不等于事件处理期间对象一定存活 |
| TimerQueue 的 ID 与两张表 | 添加、取消和扫描均无内部锁 | 实际注册线程与扫描线程之间需要同步；TaskScheduler 声明的 mutex 未用于这些操作 |
| RtmpServer 会话表、RtmpSession 的 Sink 与缓存 | 各自有 mutex，部分方法持锁调用下层对象 | 容器锁之外还要检查锁顺序、回调以及连接成员 |
| 播放连接的 is_playing_、has_key_frame 和 Chunk 解析状态 | 分发时可能从发布线程调用；关闭和协议处理还会从其他路径访问 | Session 锁和写队列锁不能统一保护这些成员 |
| ConnectionManager 登记表 | Add/Query/Rmv 加锁，Size 和析构中的清表未加锁 | 登记表锁不保护 SigConnection 的 state_、conn_、objectes_ |

例如播放连接在 SendMediaData 中更新播放标志，HandleDeleteStream 又会清标志并调用 rtmp_chunk_->Clear。跨线程写失败可能触发这条关闭路径，与连接所属线程中的 Parse 交错；业务读回调执行时已不持有连接锁，因此不能用写队列的锁证明解析状态也受保护。

还要区分“单次访问加锁”与“多步操作整体完成”：HasPublisher 检查和 AddSink 登记在不同锁区，两条连接可能都先通过无发布者检查，再分别登记。各方法内部有锁，并不自动保证“检查后登记唯一发布者”作为一个整体完成。

单调度线程并不表示整个服务只有一个访问者：主线程会 Stop/析构，定时器注册也可能发生在主线程。反过来，某个普通成员没有锁，也不能在没有第二条访问路径的情况下直接判定发生了竞争。

### 3.3 对象何时开始暴露给其他线程

TcpConnection 基类构造时就注册 Channel；之后才完成派生类初始化，TcpServer 也在 OnConnect 返回后才保存连接并设置断开回调。

当接入发生在 0 号线程、连接分配到另一调度器时，新线程可能已经分派事件，而这些初始化还没完成。这里需要的是“对象和回调准备好以后再开放事件”的发布顺序；仅给连接表增加一把锁不能补齐它。

## 4. 连接关闭：从入口到实际 socket 释放

### 4.1 当前有哪些关闭入口

| 入口 | 当前路径 | 边界 |
| --- | --- | --- |
| 主动断开 | DisConnect → 持连接锁 → Close | 在调用者线程同步执行 |
| 读失败 | HandleRead 中 Read 返回负数 → Close | 当前把负数直接当关闭条件，需复用阶段四对可重试错误的分析 |
| 业务读取回调返回 false | 读锁释放后执行 readCb_，false 时重新加锁 → Close | 业务回调可能已经执行了发送或清理 |
| 写失败 | HandleWrite 持锁写出，返回负数 → Close | Send 立即写出时，不一定在连接所属线程 |
| 挂断或错误事件 | Channel → HandleClose/HandleError → 持锁 → Close | 本批事件中的其他回调是否仍会进入，需继续检查 |

`BufferReader::Read` 走到 recv 分支时会返回其结果，但 HandleRead 没有为系统 `recv()==0` 单独进入 Close。包装函数还可能在缓冲增长限制分支返回 0，不能把它的所有零返回都当成 EOF。后续判断清理是否发生时，要确认是否实际进入了 Close。本处沿用阶段四与阶段七的关闭路径。

### 4.2 Close 的真实顺序

```text
调用者已经持有连接 mutex_
  → Close 检查 is_closed_
  → 置 is_closed_=true
  → TaskScheduler::RmoveChannel：从 epoll 注销并移除 channels_ 表项
  → closeCb_(shared_from_this())：业务清理
  → disconnectCb_(shared_from_this())：TcpServer::RemoveConnection
  → 返回调用者，随后释放连接锁
```

ENET 的 EpollTaskScheduler::RmoveChannel 正确覆盖了基类接口，会实际执行事件注销和表项移除。

Close 没有直接调用 `close(socket)`，也没有等待写队列发送完毕。`TcpConnection::~TcpConnection` 才根据 Channel 中的 fd 调用系统 close，当前判断为 `fd > 0`。Channel 析构本身不关闭 socket。

如果逻辑已关闭但仍有强引用，fd 和写队列占用的内存都可能继续存在；待发数据不会因为 Close 自动排空或获得对端确认。是否丢弃尾部数据应与具体停止需求分开判断。

### 4.3 为什么回调参数有 shared_ptr 仍不够

closeCb_ 与 disconnectCb_ 的参数，在各自调用期间提供临时强引用。但临时引用通常只活到该次调用表达式结束，不保证整个 Close、HandleWrite 或 HandleClose 栈都持有对象。

一种需要防住的时序是：

```text
epoll 通过 Channel* 调用连接方法，外层没有局部强引用
  → Close 的业务回调移除业务登记
  → disconnectCb_ 移除 connects_ 中最后一个长期持有
  → 回调参数的临时 shared_ptr 销毁，连接可能立即析构
  → 外层连接方法仍要返回，甚至还要解锁该连接的 mutex_
```

只有在“长期引用确已全部移除、外层也没有其他持有者”等条件满足时才会出现这项风险；不是每次 Close 都会立即销毁对象。阅读时要找到覆盖整次分派或关闭操作的持有者，不能只停在 shared_from_this 这个函数名。

is_closed_ 对顺序重复 Close 有局部防护，但没有解决上述寿命、锁外读取以及业务层重复 Clear 等问题。

### 4.4 TcpServer::Stop 为什么还不能视作完整停机

当前 Stop 在 is_stared_ 为 true 时：

```text
遍历 connects_
  → 对当前连接 DisConnect
  → 最后 Acceptor::Close
  → is_stared_=false
```

对尚未关闭且已设置断开回调的连接，DisConnect 会同步触发 disconnectCb_，进而从同一个 connects_ 容器删除当前元素。range-for 的内部迭代器随后还要继续递增，已不再有效；把每个元素复制到局部变量，并不能保护原容器的遍历。

此外，监听是在遍历之后才关闭，连接表没有与工作线程建立统一停机同步，Stop 也不会停止 EventLoop 或等待工作线程。本阶段应认清这些缺口，不把“调用 Stop 返回”当成整个服务已安全回收的证明。

## 5. 对象存活：从持有关系判断能否销毁

### 5.1 网络层的强引用和裸引用

```text
main
  ├─ EventLoop
  │    ├─ shared_ptr<TaskScheduler> → 基类中的 TimerQueue、EpollTaskScheduler 中的 channels_
  │    └─ shared_ptr<std::thread> → 运行 TaskScheduler::Start
  └─ 服务对象
       └─ TcpServer::connects_ ──强引用──> TcpConnection
                                           ├─ shared_ptr<Channel>
                                           ├─ unique_ptr<BufferReader/BufferWriter>
                                           └─ TaskScheduler*（借用）

EpollTaskScheduler::channels_ ──强引用──> Channel
Channel 的回调 ──裸 this──> TcpConnection
epoll_event.data.ptr ──裸指针──> Channel
```

线程函数接收的也是 scheduler.get() 裸指针。EventLoop 必须在工作线程退出前保留调度器；连接需要访问调度器完成注销时，调度器也必须仍然有效。

Channel 被调度器持有，不等于连接被 Channel 持有。将连接从 connects_ 移除后，Channel 中捕获的 this 可能失效，即使 Channel 本身暂时还在。

### 5.2 EPOLL_CTL_DEL 不会清空已返回的事件数组

```text
epoll_wait 已将 Channel* 放入本轮 events 数组
  → 另一路关闭连接，注销事件并释放持有者
  → 调度线程继续处理本轮数组中的旧地址
```

当前 HandleEvent 没有在分派前取得局部 Channel 强引用，也没有把分派与移除放到同一同步协议中。仅从 channels_ 删除不一定马上悬空，因为连接可能还持有 Channel；当全部持有者随后释放，旧地址才失去存活保证。

同一次 Channel::HandleEvent 还可能先读、再写、再处理 HUP/ERR。读回调里的关闭不意味着当前事件分派已经结束。需要保留的不只是 socket，而是仍在执行方法的连接、Channel 及其回调目标。

### 5.3 信令与 RTMP 额外持有什么

| 位置 | 持有方式 | 关闭时的含义 |
| --- | --- | --- |
| ConnectionManager::connMaps_ | 强持信令连接 | 从 TcpServer 移除不一定使它析构，还需移除信令登记 |
| 控制连接 SigConnection::conn_ | 强持目标连接 | 目标逻辑关闭后，控制方仍可能延长旧目标对象与 fd 的寿命 |
| RtmpServer::rtmp_sessions_ | 强持 Session | 3 秒清理从表中删除后，还要看是否有其他强引用 |
| RtmpConnection 到 server、session | weak_ptr | 本身不延长服务或会话寿命，lock 成功才取得临时持有 |
| Session 到 Sink、publisher | weak_ptr | 连接仍能被 lock，不表示它尚未逻辑关闭 |
| 1 毫秒 RemoveSink 定时回调 | 强捕获 session、conn | 即使已从连接表移除，回调仍可能保留这两个对象 |

另一个能说明“锁和所有权不同”的例子是 LoadBanceServer::monitorInfos_：它保存指向接收缓冲内部的 Monitor_body*，不是独立分配的对象。给 map 加锁不能延长那块缓冲的有效期，析构时 delete 这种借用地址也不正确。这里复用阶段六结论，不重做资源上报分析。

## 6. 业务清理：信令与媒体分别完成什么

### 6.1 信令 Clear 与 TCP 关闭的边界

忙碌连接收到信令 DELETESTREAM 时，HandleDeleteStream 会直接调用 Clear。这条业务路径不设置基类 is_closed_，也不注销 Channel、移出 TcpServer::connects_ 或关闭 socket：信令状态 CLOSE 与传输层关闭需要分别判断。

由传输层关闭触发的清理路径为：

```text
TcpConnection::Close
  → closeCb_ → SigConnection::DisConnected → Clear
  → 清空自己的 conn_，状态置 CLOSE
  → 对每个关联方 RmoveCustom，发送 DELETESTREAM
  → 清空 objectes_，移除自己的信令登记
  → 返回 Close，再由 disconnectCb_ 移出 TcpServer
```

Clear 中发送给其他连接的通知也是同步调用 Send，可能立即写出并进入其他关闭路径。ConnectionManager 的锁在 QueryConn 返回前释放，返回的局部 shared_ptr 保留查询到的连接，但不会锁住该连接的成员。

`RmoveCustom()` 从关联方的列表移除识别码，列表变空时把该连接置为 `IDLE`。关联方的 `conn_` 仍可能持有已清理的目标，即使业务状态已空闲，对象也要等这份强引用和其他持有者释放后才能析构。

`~SigConnection` 还会调用 Clear。例如服务端控制连接 A 仍通过 conn_ 持有已经关闭的旧 B；新 B 使用相同 code 登记后，A 才释放旧 B。旧 B 析构时再次 Clear，而 RmvConn 只按 code 删除，就可能误删新 B 的登记。因此重复清理还要核对登记对应的对象身份，不能只检查旧连接的 is_closed_。这里理解这条条件路径即可，无需另做重连实验。

### 6.2 RTMP 的延迟移除为什么要保留对象

```text
当前实现识别的 RTMP DeleteStream 命令，或 Close → OnClose
  → HandleDeleteStream
  → 在连接自己的 TaskScheduler 注册 1 毫秒任务
       捕获 [session, conn]
       到期后 session->RemoveSink(conn)，返回 false
  → 当前调用继续通知事件、清标志和 Chunk 状态
```

源码按大写 `DeleteStream` 匹配，小写 `deleteStream` 不会命中这一分支。单独处理这条命令也不调用基类 Close，清流与关闭 TCP 仍需分别判断。

媒体分发持会话锁调用连接方法。如果在这条栈上立即 RemoveSink，会再次请求同一会话锁。延迟执行将移除与当前分发栈分开；它不是“睡 1 毫秒后对象必然安全”，也不是等待所有回调结束。

需要同时看到三件事：

1. 任务必须等所属调度器再次扫描，1 毫秒是间隔，不是完成时限。
2. 强捕获保证 session 与 conn 在该任务持有期间存活，也可能延长连接 fd 的寿命。
3. 调度器先停止时，任务可能没有执行。队列最终销毁会释放捕获引用，但不会补执行 RemoveSink 等业务清理。

3 秒服务级回调再通过 GetClients 判断是否移除空 Session。连接关闭、Sink 移除、Session 移出服务表和最终析构，仍是不同步骤；发布者离开也不会在 RemoveSink 中自动关闭所有播放器。更具体的会话标志边界复用阶段九。

## 7. 锁顺序、定时器取消与回调目标

### 7.1 哪些调用发生在锁里面

| 调用位置 | 当前锁范围 |
| --- | --- |
| TcpConnection::readCb_ | recv 的连接锁已释放后调用 |
| Close 的 closeCb_、disconnectCb_ | 仍在调用者持有的连接锁范围内 |
| RtmpSession::SendMediaData / SendMetaData | 持会话锁调用播放连接方法 |
| RtmpServer::NotifyEvent | 持服务锁调用已注册事件回调 |
| TimerQueue::HandleTimerEvent | 同步执行回调，但队列没有内部 mutex |

所以不能笼统地说“所有回调都在连接锁内”，也不能假定回调会自动异步执行。当前 RTMP 事件回调只打印日志，但若回调再调用需要同一服务锁的方法，就要重新检查重入关系。

### 7.2 项目里一条有具体条件的锁顺序风险

```text
0 号线程：3 秒清理
  → 持服务锁 R
  → GetClients 等待会话锁 S

另一线程：媒体分发
  → 持会话锁 S
  → 调播放连接 Send，立即写出失败
  → 持连接锁 C 进入 Close → OnClose → HandleDeleteStream
  → NotifyEvent 等待服务锁 R
```

当清理线程持有 R 等待 S，而分发线程持有 S 等待 R 时，就会形成相互等待，可能死锁。这需要会话清理与同步写失败关闭并发等条件，并非每次分发都会发生。

1 毫秒延迟只把 RemoveSink 移出当前栈，NotifyEvent 仍在同一关闭栈中同步获取服务锁。因此延迟移除并未消除这条锁顺序风险。

本阶段学到能沿两条现有调用链画出等待关系即可，不要求先重构发送线程、锁结构或媒体分发。

### 7.3 定时器取消不是等待回调结束

TimerQueue 的添加、取消和扫描直接访问两张表，没有加锁或任务投递。EventLoop 已启动线程之后，主线程中的服务构造仍会注册任务，双方没有建立完整同步。

RemoveTimer 删除记录，不提供“等待已经开始的回调返回”的保证；当前扫描在回调返回后还继续使用 events_.begin()。回调直接删除自己可能改变或清空正在处理的记录，简单一次性任务应使用返回 false 的既有约定。

| 任务 | 注册与捕获 | 当前销毁边界 |
| --- | --- | --- |
| LoginServer 1 秒资源上报 | 连接负载成功后通过 EventLoop 注册；捕获裸 this，保存 id_ | 析构没有取消；client_ 销毁时回调仍可能访问它 |
| RtmpServer 3 秒空会话清理 | 通过 EventLoop 注册；捕获裸 this，没有保存 TimerId | 析构没有取消，不能保证以后不再访问服务成员 |
| RtmpConnection 1 毫秒移除 Sink | 在自己的调度器注册；强捕获 session、conn | 保留对象直到任务释放；停止循环不保证已执行清理 |

LoadBanceServer 本身没有周期过期清理任务，其资源表不会由这类定时回调自动清扫。

销毁捕获目标之前，应同时满足“不再有后续回调进入”和“已经进入的回调已结束”。取消与等待要在有同步保证的前提下协调；当前接口不具备完整协议，不能直接在析构中补一个无同步 RemoveTimer 就认定修复完成。

## 8. 线程退出与整个服务的停机顺序

### 8.1 EventLoop::Quit 当前确实做了什么

```text
EventLoop::Quit
  → 依次对所有调度器 Stop：is_shutdown_=true
  → 对所有 joinable 的工作线程 join
  → 清空 task_schdulers_ 和 threads_ 中的引用
```

工作线程执行 `扫描定时器 → HandleEvent → 下一轮检查标志`。当前 `epoll_wait(..., 0)` 立即返回，外层循环也没有空闲等待，因此会反复扫描，可能使空闲 CPU 占用偏高。当前没有停止唤醒机制，但这里也没有阻塞在 epoll_wait 中；不能仅因没有 eventfd 就断言空闲线程必然退不出。若以后改成阻塞等待，才必须一起解决停止唤醒和定时器期限。

慢回调、同步数据库调用、锁等待或解析无进展循环都可能阻止工作线程回到检查点。HandleEvent 返回 false 也没有被 Start 用来终止循环。停止请求不负责强行打断这些执行。

Quit 不能在它要等待的工作线程中同步完成自 join。一次成功 Quit 会清空两个容器，随后顺序再次调用为空操作；并发 Quit，以及退出过程中继续注册工作，则没有统一状态协议。

### 8.2 原子类型仍挡不住这条启动时序

```text
主线程创建工作线程，但工作线程尚未进入 Start
主线程立即调用 Quit → Stop，将 is_shutdown_ 置 true
工作线程进入 Start，开头又写 is_shutdown_=false
工作线程继续循环，主线程在 join 中等待
```

这是停止请求被后来的启动重置覆盖，不是原子读写撕裂。当前代码缺少启动完成与停止协调；重复 sleep 不能建立可靠顺序。

清空 EventLoop 的调度器引用也不保证调度器立即析构，因为 GetTaskSchduler 会向外返回 shared_ptr。即使调度器尚在，已经 join 的工作线程也不会替残留任务继续执行。

### 8.3 当前 main 的析构顺序还有哪些空隙

三个使用 getchar 的服务在输入返回后离开 main，局部服务对象先于之前创建的 EventLoop 析构。此时工作线程还在运行。以 LoginServer、RtmpServer 为例，派生析构体为空；一旦开始销毁，会先销毁派生成员，再进入 TcpServer 基类析构的 Stop。基类 Stop 无法提前保护这些已经开始销毁的派生成员。

RtmpServer 的 main 则一直 sleep，没有正常跳出循环的入口。默认 Ctrl+C 或强制结束进程，不能用来证明 C++ 的 Stop、Quit 和析构链已经走完。

安全顺序应按依赖理解，下面是**需要满足的条件，不是当前已经实现的完整流程**：

1. 由工作线程之外的协调者阻止本次服务的新接入、新业务提交与重复启动，并协调停止继续产生新业务的周期任务。关闭通知和延迟移除等清理回调的执行、等待或撤销，按后续步骤协调。
2. 保留服务、连接和调度器，完成现有连接的逻辑关闭与事件注销；关闭过程中仍会用到的回调和对象不能提前释放。
3. 若选择完成延迟移除，应让相应调度器还有机会执行；若选择停止后直接释放残留任务，也要另有业务清理安排。不能依赖一个已经退出的线程执行最后一次回调。
4. 发出停止请求，确保当前处理可以返回；等待期间不持有工作线程所需的锁，再 join 所有相关工作线程。
5. 确认不会再进入、也没有正在执行的相关回调后，释放剩余持有者及资源。若某项清理仍需使用调度器，就必须在调度器销毁前完成。

停止一条连接时不需要退出整个 EventLoop；整个服务停机才需要覆盖全部接入、定时器、连接与线程。对象最终释放顺序由这些依赖决定，不能只机械地“先析构服务”或“先销毁调度器”。

### 8.4 三类 fd 分别在哪里释放

| fd | 当前释放位置 | 当前缺口 |
| --- | --- | --- |
| 已接入连接 socket | TcpConnection 析构中 close，判断 fd > 0 | 逻辑 Close 不直接释放；fd 0 的合法边界被漏掉 |
| 监听 socket | Acceptor::Close → TcpSocket::Close | Bind/Listen 失败后服务未置 is_stared_，Stop 跳过清理；Acceptor 与 TcpSocket 析构体为空 |
| epoll fd | 无显式释放 | EpollTaskScheduler 构造中创建，析构为空，未显式 close(epollfd_) |

停止线程或销毁 Channel 不能代替这些释放操作。进程结束后操作系统回收 fd，只能说明进程资源被回收，不能据此证明服务自身支持连接回收、重复启动或正常停机。

## 9. 学习步骤与必要观察

### 第一步：复用线程图，选几项共享状态

按第 3 节定位 is_shutdown_、is_closed_、connects_ 和 TimerQueue。逐项回答“谁读、谁写、是否可能同时发生、保护到哪里”。已能解释的同步概念直接略过，不另写并发入门程序。

### 第二步：跟一条连接从关闭到析构

从 DisConnect 或一次真实关闭入口跟到 Close、业务回调和 RemoveConnection。对照第 5 节持有图，指出每次移除后还有谁保留连接、当前调用栈靠什么存活，以及 socket 最后在哪里 close。

再看 TcpServer::Stop 的遍历与同步删除，解释为什么“有 shared_ptr”和“Close 做了标志检查”还不够。

### 第三步：把业务清理、锁顺序与 Quit 接起来

跟一次信令 Clear 或 RTMP HandleDeleteStream；若选 RTMP 路径，再确认延迟任务属于哪个调度器、捕获谁。沿第 7.2 节的两条调用链解释锁顺序，再用第 8.2 节时序说明 atomic 与停机协议的区别。

最后对照实际 main，说明哪些对象在工作线程结束前开始析构，哪些定时回调仍可能进入。

### 第四步：按现成条件观察，不另设一轮完整联调

复用已有服务、连接或阶段九的一推一拉记录。有运行条件时，只观察一次连接收发、主动断开和现有退出入口，使用已有日志或断点核对 Close、RemoveConnection、RemoveSink、析构与线程返回；顺手查看空闲 CPU 即可。

若需要辨认线程或 fd，可按需查看当前进程的线程列表和 `/proc/<pid>/fd`；fd 总数变化要结合具体持有关系解释。RtmpServer 没有正常退出入口、EOF 未触发关闭或某次 join 无法完成时，定位已到达的步骤即可，不把强制结束进程标为正常停机通过。

没有现成运行条件时先完成源码推演，实际线程退出和跨端停止保留到阶段十二验证。无需新建服务、退出框架或测试矩阵，也不要求先修完全部缺口；慢读、快速重连、压力测试和 sanitizer 专项检查只在问题需要时选用。
