## 2. 先看整体链路：两次返回的地址不同

以下端口来自当前源码，IP 有多处硬编码，运行前需要核对实际配置。

| 服务 | 源码默认端口 | 接收什么、返回什么 |
| --- | --- | --- |
| `LoadBanceSvr` | 8523 | 接收登录服务的资源上报；向客户端返回一个登录服务地址 |
| `LoginSvr` | 9867 | 接收用户登录信息；查询数据库后返回结果及信令地址 |
| `SigSvr` | 6539 | 处理后续信令，具体业务放到阶段七 |
| 数据库 | 3306 | 供登录服务执行 SQL，客户端不会沿这条链路直连数据库 |

`LoginReply` 中是登录地址，`LoginResult` 成功分支中是信令地址。负载服务只帮助发现入口，后续登录流量由客户端直接发给登录服务。

```text
LoginSvr ── Monitor_body ──> LoadBanceSvr
                               ↑       │
                    Login_Info │       │ LoginReply：登录地址
                               │       ↓
                             客户端
                               │
                         连接 LoginSvr
                               │ UserLogin
                               ↓
                            LoginSvr ── SQL ──> 数据库
                               │
                               └── LoginResult：结果码、信令地址 ──> 客户端
```

`Login_Info` 是入口查询，`UserLogin` 是用户登录请求，二者虽然都使用 `Login` 命令值，结构和长度却不同。必须结合“发给哪个服务、处于哪个步骤”解释报文。报文布局与拆包方法沿用阶段二、四，本阶段不再重做。

两步的错误表示也不同：入口查询超时时，负载服务把回复的 `cmd` 设为 `ERROR`；用户登录超时时，登录服务通过 `LoginResult.resultCode` 返回 `REQUEST_TIMEOUT`。判断结果时要读取对应报文的字段。

这张图描述预期业务路径。下面会逐步区分源码已经做了什么，以及哪些实现问题会影响实际运行。

## 3. 资源怎样上报、保存和选择

### 3.1 首次上报发生在构造阶段

沿 `LoginServer::LoginServer()` 阅读：

```text
创建 TcpClient
  → Create()：打开 /proc/meminfo，取得 sysinfo，创建 socket，设置上报地址
  → Connect(负载服务地址, 8523)
  → 连接成功：立即 getMonitorInfo()
  → 注册间隔 1000 毫秒的重复定时器
  → 后续由事件循环执行定时上报
```

这里有三个容易误读的地方：

- 首次上报是构造函数中的直接调用，后续上报才是定时回调。
- `main` 在 `LoginServer::Create(...)` 返回后才调用监听接口 `Start(...)`，所以“已经上报地址”不等于“登录端口已经可接入”。
- 初次连接负载服务失败后，当前代码没有重试或重连；即使登录端口随后成功监听，负载服务也可能没有它的入口记录。

定时回调的线程、延迟和取消问题沿用阶段五。此处的 `TcpClient::Send` 是直接调用阻塞 socket 的发送循环，没有走阶段四的 `TcpConnection/BufferWriter` 路径；周期发送阻塞时会拖住执行该回调的线程。

### 3.2 上报的是内存指标，不是通用负载评分

`Monitor_body` 包含 `mem`、`ip`、`port`。地址和端口表示登录服务声明的接入位置，当前端口写为 9867。

`get_mem_usage()` 尝试用 `sysinfo` 的总内存与 `/proc/meminfo` 的 `MemAvailable` 估算内存占用百分比，再转成 `uint8_t` 写入 `mem`。它没有统计 CPU、连接数或在线人数。

先分清两个量的含义与单位：`MemAvailable` 是无需换出内存即可供新应用使用的内存估计量，包含部分可回收内存，和 `MemFree` 不同，见 [Linux /proc 文档](https://docs.kernel.org/filesystems/proc.html)。`sysinfo.totalram` 则以 `mem_unit` 字节为一个计数单位，见 [sysinfo 手册](https://man7.org/linux/man-pages/man2/sysinfo.2.html)。统一为字节后，计算关系是：

```text
totalBytes = totalram × mem_unit
availableBytes = MemAvailable 的 kB 数值 × 1024
估计占用率 = (totalBytes - availableBytes) / totalBytes × 100%
```

例如，总量为 8 GiB、可用量为 3 GiB 时，估计占用率为 62.5%。当前代码的整数运算会截掉小数部分；这里只用公式理解指标，不要求另写采集程序。

但当前采集代码不能视为可靠的实时指标：

1. `/proc/meminfo` 只打开一次，读到 `MemAvailable` 后停住，下一次没有回到文件开头。后续读取可能走到 EOF，`avimem` 留为 0，从而算出 100。
2. `sysinfo` 只在 `Create()` 调用一次，计算总内存时没有处理 `mem_unit`。

因此，观察到持续上报并不能证明资源采集正确。先看文件位置、字段来源和计算方式，再解释 `mem` 的值。

### 3.3 选择规则很简单

负载服务按上报连接的 fd 保存记录：

```cpp
monitorInfos_[fd] = info;
```

这里的 fd 是负载服务接收上报的连接标识，不是登录服务监听端口。

`GetMonitorInfo()` 把 map 中的键值对放进 vector，按 `mem` 从小到大排序，返回第一项。假设两条记录都有效且内容稳定：

| 上报连接 fd | 登录地址 | mem |
| --- | --- | --- |
| 40 | A:9867 | 60 |
| 41 | B:9867 | 20 |

这次查询会选择 B。当前规则不包含轮询、连接数评分或明确的同分优先级；理解这一次选择就够了，无需为本阶段部署两套登录服务。

### 3.4 保存了指针，不等于保存了记录

沿 `HandleMinoterInfo() → UpdateMonitor()` 看指针来源：

```cpp
Monitor_body* body = (Monitor_body*)buffer.Peek();
server->UpdateMonitor(socket_, body);
```

`body` 指向该连接的接收缓冲区。`UpdateMonitor` 没有复制结构体，也没有为记录分配独立存储。

```text
接收缓冲区中的字节
       ↑
Monitor_body* body
       ↑
monitorInfos_[fd] 保存同一个地址
```

`Retrieve` 消费数据后，字节可能暂时还在原处，但该地址已不能当作稳定的历史记录使用。后续接收覆盖、缓冲区移动或连接销毁都会影响它。map 的锁只保护表操作，不能延长接收缓冲区内数据的有效期。

另外还有两处问题：

- `GetMonitorInfo()` 在表为空时直接访问 `vec[0]`，没有可靠的“无可用服务”返回路径。
- 当前没有记录最后上报时间、失联删除和有效期淘汰；析构函数却对借用的记录指针执行 `delete`，与其来源不匹配。

合理的管理方式是：表中持有独立的记录值，收到上报时记下本地单调时钟的时刻，查询时排除已经断线或距离最近上报超过失联阈值的记录。这个时间用于判断资源记录是否新鲜，与客户端请求中的 Unix 时间戳分开使用。

失联阈值需要容许多个上报周期和调度延迟，不能直接把 1000 毫秒上报间隔当作失效期限。本阶段先理解这些条件，当前源码尚未实现相应管理逻辑。

## 4. 数据库先补这几个概念

### 4.1 区分 SQL 执行、结果集、行和字段

对于本项目使用的 MySQL C API，可以按以下顺序理解：

```text
mysql_query：执行 SQL
  → mysql_store_result：取得并保存结果集
  → mysql_fetch_row：从结果集中取得一行
  → 复制业务还需要的字段
  → mysql_free_result：释放结果集
  → 业务继续使用自己拥有的数据
```

必须分清下面几种情况：

| 观察位置 | 含义 |
| --- | --- |
| `mysql_query(...)` 的返回值 | 0 表示 SQL 执行成功，非 0 表示失败；成功不代表查询一定有匹配行 |
| SELECT 成功后，`mysql_store_result(...) == nullptr` | 取得结果集失败，不能直接当作“没有这个用户” |
| 结果集非空指针，但第一次 `mysql_fetch_row(...) == nullptr` | 在本项目的 `store_result` 用法下，查询没有返回行 |
| `row` 有效，但某个 `row[n] == nullptr` | 该字段是 SQL `NULL`，不能直接交给 `atoi` 等函数 |
| `row[n]` 指向空字符串 | 字段有值但长度为 0，与 SQL `NULL` 不同 |

空结果集仍可对应非空的 `MYSQL_RES*`。详细接口语义见 [mysql_query](https://dev.mysql.com/doc/c-api/8.4/en/mysql-query.html)、[mysql_store_result](https://dev.mysql.com/doc/c-api/8.4/en/mysql-store-result.html) 和 [mysql_fetch_row](https://dev.mysql.com/doc/c-api/8.4/en/mysql-fetch-row.html)。这些是 API 参考，不要求更换阶段零已配置的兼容客户端库。

### 4.2 MYSQL_ROW 不拥有字段数据

`MYSQL_RES` 管理查询结果的存储，`MYSQL_ROW` 是借用的行数据。复制 `MYSQL_ROW` 或复制里面的 `char*`，都没有复制字段内容。

```cpp
MYSQL_ROW row{mysql_fetch_row(result)};
// 此处先检查 row 和所需字段。
std::string code{row[3]};
mysql_free_result(result);
// 后面使用 code；不能再读取 row[3]。
```

上面展示的是复制顺序，字段下标来自当前项目的预期表顺序。字符串副本拥有自己的内容，可以在结果集释放后继续使用。释放语义见 [mysql_free_result](https://dev.mysql.com/doc/c-api/8.4/en/mysql-free-result.html)。

再读 `ORMManager::selectClientByUsercode()`，会看到相反的顺序：

```cpp
row = mysql_fetch_row(res);
mysql_free_result(res);
return row;
```

有行时，这个返回值已经悬空。`HandleLogin` 随后读取 `row[4]`、`row[0..3]`，可能碰巧读到旧内容，也可能出错；一次运行成功不能说明代码正确。

学习时先用“复制所需字段后释放”的小片段观察有效期，不需要故意运行悬空指针来验证问题。若继续修复项目，应让查询接口返回拥有字段内容的业务值，并保留“无用户”和“查询失败”的区别；单纯延后释放却没人负责释放，也不完整。

### 4.3 INSERT 和 UPDATE 对应不同业务动作

- `INSERT`：新增记录，适用于注册新用户。
- `UPDATE ... WHERE USER_CODE = ...`：修改已有用户，适用于登录后更新在线标记和最近登录时间。
- `DELETE ... WHERE USER_CODE = ...`：删除记录，当前 `Destory` 走这条路径。

例如，已有用户登录后的预期状态变化可用下面的 SQL 表达：

```sql
UPDATE clients
SET USER_ONLINE = 1, USER_RECENTLY_LOGIN = UNIX_TIMESTAMP()
WHERE USER_CODE = '345';
```

这是语义示例，不是要求现在执行的修改。`UPDATE` 修改现有行，详见 [MySQL UPDATE](https://dev.mysql.com/doc/refman/8.4/en/update.html)。

SQL 执行成功与业务成功还隔着一步：例如，`UPDATE` 没有匹配到用户时，也可能没有 SQL 错误。业务需要结合实际记录和操作结果判断，不能只凭“调用过数据库函数”回复成功。

## 5. 从 ORMManager 跟到登录结果

### 5.1 数据库什么时候连接，连接到哪里

`ORMManager::GetInstance()` 用 `std::call_once` 创建单例，第一次业务调用时才构造数据库连接。

当前连接参数：

| 配置 | 源码值 |
| --- | --- |
| 主机、端口 | `127.0.0.1:3306` |
| 用户、数据库 | `root`、`users` |
| 密码 | 从进程环境变量 `ENET_DB_PASSWORD` 读取 |

数据库位于 Linux 服务进程所见的本机地址。Windows 客户端能够连到登录端口，不代表 Linux 进程能连上这个数据库。

环境变量缺失或建连失败时，构造函数会抛出异常；当前业务回调没有相应的捕获和回复路径。因此不能把所有数据库配置错误都解释为“客户端收到 `SERVER_ERROR`”。

`call_once` 只保证单例初始化一次，不保证后续所有 SQL 操作都自动具有线程同步。当前 `LoginSvr` 使用单工作线程事件循环，`mysql_query/mysql_store_result` 同步执行，慢查询会拖住这个线程上的其他连接回调和周期任务。此处先认清阻塞位置，无需立即设计异步数据库层。

### 5.2 表结构没有随仓库提供，需要核对字段顺序

仓库未提供建表 SQL。`HandleLogin` 通过 `row[0..4]` 读取前五列，因此这些列必须与下表的 0～4 项对应。后两列当前未按下标使用；表中 5、6 项的排列是实验 DDL 的选择，不能据此还原原表的完整列序。

| 本例下标 | 列名 | 用途 |
| --- | --- | --- |
| 0 | `USER_NAME` | 用户名 |
| 1 | `USER_ACOUNT` | 账号，保留源码中 `ACOUNT` 的拼写 |
| 2 | `USER_PASSWD` | 密码字段 |
| 3 | `USER_CODE` | 查询用识别码 |
| 4 | `USER_ONLINE` | 在线标记，登录处理调用 `atoi(row[4])` |
| 5 | `USER_RECENTLY_LOGIN` | 最近登录时间 |
| 6 | `USER_SVR_MOUNT` | 保存的服务地址字段，当前登录成功回复并未从这里取地址 |

`INSERT` 显式写了列名，但查询是 `SELECT *`。如果实际表在最前面增加自增 ID，`row[4]` 就不再是在线标记。已有表先用 `SHOW COLUMNS FROM clients;` 核对，不要直接照抄新建。

只有缺少实验表时，才在独立的本地实验数据库中使用下面的最小设计。数据库名需与源码中的 `users` 一致；若该名称已被真实数据使用，应改用独立实例或调整实验连接配置。列类型、非空约束和主键是这里为实验选择的，不能当作仓库原有 DDL。

执行前确认：Linux 侧数据库实例已启动，实验库 `users` 已创建，并允许使用源码配置的账号、密码通过 `127.0.0.1:3306` 连接。阶段零准备的开发文件只满足编译需要，这些运行条件仍需单独确认；已有环境采用其他实验账号时，同步调整服务与下方片段的连接参数。

```sql
USE users;

CREATE TABLE clients (
    USER_NAME VARCHAR(64) NOT NULL,
    USER_ACOUNT VARCHAR(64) NOT NULL,
    USER_PASSWD VARCHAR(128) NOT NULL,
    USER_CODE VARCHAR(20) NOT NULL,
    USER_ONLINE TINYINT NOT NULL DEFAULT 0,
    USER_RECENTLY_LOGIN BIGINT NOT NULL DEFAULT 0,
    USER_SVR_MOUNT VARCHAR(64) NOT NULL,
    PRIMARY KEY (USER_CODE)
);

INSERT INTO clients (
    USER_NAME, USER_ACOUNT, USER_PASSWD, USER_CODE,
    USER_ONLINE, USER_RECENTLY_LOGIN, USER_SVR_MOUNT
) VALUES (
    'stage6_demo', 'demo', 'test_only', '345',
    0, UNIX_TIMESTAMP(), '127.0.0.1'
);
```

这个合成用户沿用当前客户端硬编码的 `345`，供本阶段的查询与后续登录观察复用。已有同码测试用户可以直接复用，不要重复插入。账号、密码和地址都是实验值。

### 5.3 HandleLogin 实际做了什么

先假设查询已经返回了有效且独立持有的用户数据，再理解业务分支；当前悬空行指针会影响这些分支的可靠执行。

```text
UserLogin
  → 检查请求时间戳
      超过阈值 → REQUEST_TIMEOUT
  → 根据 GetCode() 查询用户
      返回空指针 → SERVER_ERROR
  → 读取在线标记
      非零 → ALREADY_LOGIN
      为零 → 设置 S_OK，填写硬编码的信令 IP 和 6539
             → 调用 insertClient(...) 尝试写入在线状态
  → Send(LoginResult)
```

注意四处业务边界：

1. 当前登录按识别码查用户，没有比较请求中的账号和密码，因此 `S_OK` 不能解释为完成密码认证。
2. 查询失败和用户不存在都会被折叠为 `nullptr`，登录分支统一回复 `SERVER_ERROR`；部分初始化异常则可能根本走不到回复。
3. 更新在线状态实际调用了 `INSERT`。按上面的主键设计，重复识别码会导致插入失败；没有唯一约束时则可能新增同码的在线行，原离线行仍然保留。后续查询没有指定顺序且只取一行，仍可能读到离线记录，使在线判断失真。`insertClient` 只打印错误，调用者仍可能发送先前设置的 `S_OK`。
4. 成功回复的信令地址硬编码为 `172.21.205.121:6539`，没有读取 `USER_SVR_MOUNT`，也没有验证信令服务当前可用。

`HandleRegister` 同样没有将插入失败反馈给结果码。`HandleDestory` 执行用户删除且没有对应业务回复；`Clear()` 为空，断线也没有在这里将在线标记复位。把这些分支读清即可，首轮不要求做注册、删除实验。

SQL 通过 `sprintf` 拼接输入，未使用参数绑定或转义；结合缺少密码校验，这套代码适合分析现有流程，不能当作完善的认证实现。此处只识别问题，不扩展成安全改造任务。

## 6. 客户端怎样走完两次查询

对照客户端 `LoginWgt.cpp` 时，只追地址与消息流，不要求先掌握 Qt 界面实现：

1. 构造时连接固定的负载地址，TCP 连接成功后自动发送 `Login_Info`。
2. 收到 `LoginReply` 后断开原连接，使用同一个 `QTcpSocket` 连接返回的登录地址。
3. 连接登录服务成功后立即发送 `UserLogin`：识别码固定为 `345`，账号和密码取当时输入框内容，可能仍为空。
4. 收到 `LoginResult` 且结果码为 0 后，发出 `sig_logined`，后续把信令地址交给远控模块。

当前代码中的 `is_login_` 用来区分响应所处阶段，不等于用户已经认证成功。

登录按钮的处理仍发送 `Login_Info`。切换到登录服务后，再点按钮不会自动重走入口发现，而可能把入口查询报文发给登录端口。不能把当前界面描述成“填好信息，点一次按钮就按标准流程登录”。

客户端使用 `readAll()` 后直接解释报文，没有完整的累积拆包与长度校验；结果失败时的界面提示也不完整。相关收包问题沿用阶段二、四，客户端实现细节留在客户端对应阶段继续阅读。

### 6.1 三种“有效”不要混在一起

| 判断对象 | 当前情况 |
| --- | --- |
| 请求时间戳是否新鲜 | 入口查询和用户登录尝试按当前 Unix 秒时间与请求时间比较，阈值为 60 秒 |
| 资源记录是否仍代表可用服务 | 没有最后上报时间、失联删除或过期淘汰 |
| 保存的数据地址是否还有效 | 监控记录借用接收缓冲区；数据库行在释放结果集后悬空 |

请求未超时，不能证明资源记录新鲜，更不能证明指针有效。两端时钟不一致会影响时间戳判断；当前代码的无符号时间差处理也有边界问题，不宜把它视为完整的时钟校验或重放防护。

## 7. 一次查询与一个失败分支怎么观察

### 7.1 先做不依赖登录链路的只读查询

已有示例能够正确展示“查询 → 复制字段 → 释放结果”时，直接复用。否则可在准备好实验表后使用下面的小片段，它只读取 `345` 的识别码和在线标记。

先在同一 Linux shell 中设置好 `ENET_DB_PASSWORD`，不要把密码写进源码。下面的编译命令以 `mysql_config` 可用为前提，用它提供现有数据库开发库的头文件和链接参数。

```bash
stage6_dir="$(mktemp -d)"
c++ -std=c++17 $(mysql_config --cflags) -x c++ - -x none \
    -o "$stage6_dir/EnetMysqlResult" $(mysql_config --libs) <<'CPP'
#include <mysql.h>
#include <cstdio>
#include <cstdlib>
#include <memory>
#include <string>

int main()
{
    char const* password{std::getenv("ENET_DB_PASSWORD")};
    if (password == nullptr)
    {
        std::fputs("ENET_DB_PASSWORD is not set\n", stderr);
        return 1;
    }

    using Connection = std::unique_ptr<MYSQL, decltype(&mysql_close)>;
    Connection connection{mysql_init(nullptr), &mysql_close};
    if (!connection)
    {
        std::fputs("mysql_init failed\n", stderr);
        return 1;
    }
    if (!mysql_real_connect(connection.get(), "127.0.0.1", "root",
                            password, "users", 3306, nullptr, 0))
    {
        std::fprintf(stderr, "%s\n", mysql_error(connection.get()));
        return 1;
    }

    char const* query{
        "SELECT USER_CODE, USER_ONLINE FROM clients WHERE USER_CODE = '345'"};
    if (mysql_query(connection.get(), query) != 0)
    {
        std::fprintf(stderr, "%s\n", mysql_error(connection.get()));
        return 1;
    }

    using Result = std::unique_ptr<MYSQL_RES, decltype(&mysql_free_result)>;
    Result result{mysql_store_result(connection.get()), &mysql_free_result};
    if (!result)
    {
        std::fprintf(stderr, "%s\n", mysql_error(connection.get()));
        return 1;
    }
    MYSQL_ROW row{mysql_fetch_row(result.get())};
    if (!row)
    {
        std::puts("no matching user");
        return 0;
    }
    if (!row[0] || !row[1])
    {
        std::fputs("unexpected SQL NULL\n", stderr);
        return 1;
    }

    std::string code{row[0]};
    std::string online{row[1]};
    result.reset();
    row = nullptr;
    std::printf("owned code=%s, online=%s\n", code.c_str(), online.c_str());
    return 0;
}
CPP
"$stage6_dir/EnetMysqlResult"
```

这里显式查询两列，所以 `row[0]`、`row[1]` 分别对应识别码和在线标记，与 `SELECT *` 的下标不同。`result.reset()` 释放结果后，输出读取的是两个 `std::string` 副本；连接和结果集由现有标准库 `unique_ptr` 管理。

按前面的实验数据，预期输出为 `owned code=345, online=0`；已有测试用户则以其实际在线标记为准。这只能说明只读查询和字段复制完成，不能证明原项目的登录处理正确。

若阶段零只解包了缓存依赖，且没有 `mysql_config`，这段编译命令不能直接执行。可复用已有能够编译运行的查询示例；暂不具备工具或数据库运行条件时，先沿片段解释字段复制与释放顺序，条件具备后再补运行观察，无需为此另搭构建工程。

### 7.2 观察无匹配用户的结果

正常查询后，把片段中的 `'345'` 换成一个确认不存在的测试识别码，再编译运行，观察 `no matching user`。该分支展示“SQL 成功但没有记录”，与拼错表名等 SQL 失败分开理解。

回到服务端源码，找到这个空结果如何被转成 `SERVER_ERROR`。不要求另外制造断网、超时、重复登录等全部异常。

不要把“没有任何登录服务上报”选作首个网络失败实验：当前 `GetMonitorInfo()` 的空 vector 访问可能直接出错，不能预期它会正常回复 `ERROR`。

### 7.3 已能启动服务时，再观察消息交接

沿用阶段零的构建结果，依次确认负载监听、登录服务上报、登录端口监听，以及数据库测试用户。核对客户端连接的负载地址、上报中的登录地址、返回的信令地址是否与环境一致；当前代码多处 IP 并不一致，不能只改一个入口地址。

用已有日志或断点观察以下交接点即可：

```text
getMonitorInfo
  → HandleMinoterInfo / UpdateMonitor
  → HnadleLogin / GetMonitorInfo
  → LoginConnection::HandleLogin
  → ORMManager::selectClientByUsercode
  → LoginResult 发送与客户端接收
```

本节是已有服务可运行时的补充观察。监控指针、数据库行指针、报文处理或环境问题阻断路径时，按阶段一的方法定位，区分“源码推演”和“实际已观察”。不需要为了通过本阶段先修完全部问题，也不把返回 `S_OK` 当作数据库写入成功的证据。

## 8. 自查与完成标准

可以直接口述或指着源码回答，不要求另写完整报告：

1. 客户端两次收到的地址分别用于什么？负载服务是否转发登录请求？
2. 首次连接负载服务失败后，为什么登录端口能监听却仍可能查不到入口？
3. `mem` 怎样产生、怎样参与选择，当前采集和过期处理缺少什么？
4. 监控表指针和数据库行指针分别借用了谁的数据，什么时候不能再用？
5. 无匹配行、SQL 执行错误、字段值为 SQL `NULL` 有什么区别？当前代码保留了这些区别吗？
6. `S_OK` 能否证明密码正确、在线标记写入成功或信令服务可连接？

完成本阶段时，应能做到：

- [ ] 沿资源上报、入口查询、用户查询和结果消费说明整条路径。
- [ ] 正确解释一次正常 SELECT 和一次无匹配用户的结果；暂不能运行时，能指出待验证位置。
- [ ] 说明“先复制再释放”、`SELECT *` 字段顺序和 `INSERT/UPDATE` 的实际影响。
- [ ] 分清预期业务、当前实现与已验证结果，不依赖悬空指针的偶然表现判断正确性。
