# ENET 阶段十二：联合联调与验收学习讲义

> 对应[项目学习规划的阶段十二](项目学习规划.md#joint-validation)。参考用时：8～12 小时，首次部署、基础补学与复杂排障另计。
>
> 使用两个客户端完成一次“A 控制并播放 B”的会话，观察正常退出，再观察一个简单失败。两端共用本讲的操作与结果，不再分别安排一轮完整验收。

## 1. 本阶段要完成什么

本阶段验证实际行为，不再从头讲 Qt、RTMP、采编或并发理论。按下面顺序推进：

1. 准备两端地址、两组识别码与已有测试数据。
2. 启动四个服务，再依次启动 B、A，确认本机信令登记。
3. A 只发起一次对 B 的远程控制，观察画面、声音和一次鼠标操作。
4. 关闭 A 的播放窗口与主窗口，再请求 B 退出，核对线程和服务端连接清理。
5. 复用本轮已有的简单失败；若需补做，按第 7 节独立观察“目标不存在”。
6. 结束服务，保留各环节实际通过、未通过或阻断的结果。

主要依据：

| 已学内容 | 本阶段怎样复用 |
| --- | --- |
| [服务端阶段零](阶段零工程与构建基线学习讲义.md)、[客户端阶段零](https://github.com/slimesq/ECloudAssistant/blob/main/docs/项目学习规划.md#stage-0) | 沿用已构建产物与运行依赖，不重新搭构建环境 |
| [阶段六](阶段六负载分配登录与数据库学习讲义.md) | 复用数据库、实验表、登录字段和已知缺口 |
| [阶段七](阶段七信令与远控状态机学习讲义.md)、[阶段九](阶段九RTMP会话与媒体分发学习讲义.md) | 对应建流、媒体分发和清理入口 |
| [阶段十](阶段十客户端接口对照学习讲义.md) | 核对两端消息、地址来源、URL、输入与成功层次 |
| [阶段十一](阶段十一并发关闭与资源回收学习讲义.md)、[客户端阶段九](https://github.com/slimesq/ECloudAssistant/blob/main/docs/项目学习规划.md#stage-9) | 解释实际停止、线程等待、对象存活和资源回收 |

## 2. 两个客户端怎样安排

### 2.1 A 控制，B 被控

| 位置 | 本轮用途 | 操作 |
| --- | --- | --- |
| A：控制端 Windows 环境 | 发起控制、播放 B 的画面声音、发送鼠标输入 | 填目标 B 的识别码，只点击一次“开始远程” |
| B：被控端 Windows 环境 | 发布自己的桌面与系统声音，执行远程输入 | 显示普通文本窗口，准备一段已有声音，不再打开自己的拉流画面 |
| ENET：Linux 环境 | 运行负载、登录、信令和 RTMP 四个服务 | 保留各服务的终端或已有调试会话 |

完整效果观察需要两个各自可用的 Windows 交互桌面和音频环境。可复用现有两台机器或符合这些条件的独立环境，不要求为本讲另建虚拟化环境。

同一 Windows 桌面上启动两个进程，只适合部分连接与协议观察。当前采集目标是 desktop，声音来自默认播放设备的 WASAPI loopback，输入最终作用于桌面；同桌面测试可能再次采入 A 的播放窗口和声音，注入输入也会影响同一个桌面，不能直接当作独立远控效果通过。

### 2.2 启动前确定四种码

本讲采用下面一组例子；使用其他短识别码时，保持对应关系即可。

| 项目 | A | B | 实际用途 |
| --- | --- | --- | --- |
| UserLogin.code：登录码 | 345 | 346 | LoginSvr 查询测试用户 |
| 本机 JOIN.id | 345 | 346 | 各自的本机信令连接登记 |
| A 填写的目标码 | 346 | 不发起控制 | OBTAINSTREAM.id 指向 B |
| A 的控制连接 JOIN.id | 固定 154564 | 不创建这条控制连接 | A 另建控制连接时使用，不能与已有登记冲突 |

登录码和本机登记码不是自动绑定的两个字段。本轮令它们取相同值，只是便于追踪；服务端并未由此完成识别码归属认证。媒体流名另由客户端生成，不能拿来替代这些码。

### 2.3 当前需要在启动前配置两处默认值

客户端当前没有读取这些码的命令行或配置文件。可在一个已有构建环境的工作副本中核对下面两处，沿用阶段零的构建步骤，分别准备 A、B 对应的产物；两端运行机器不必各自安装编译环境：

- [LoginWgt.cpp](https://github.com/slimesq/ECloudAssistant/blob/main/UI/center/LoginWgt.cpp) 的 `login.SetCode(...)`：A 为 `"345"`，B 为 `"346"`。
- [RemoteWgt.cpp](https://github.com/slimesq/ECloudAssistant/blob/main/UI/center/RemoteWgt.cpp) 的 `selfCodeEdit_->setText(...)`：A 默认 345，B 默认 346。

已有相应配置和产物时直接复用。保留各自完整的运行目录及匹配 DLL、Qt 插件，避免准备 B 时覆盖了要给 A 使用的产物；无需为这次联调新增配置系统。

原因是现有启动会自动推进：

```text
构造 LoginWgt → 查询负载 → 切换登录服务 → 自动发送 UserLogin
  → 成功 LoginResult → sig_logined
  → RemoteWgt::handleLogined 读取当时的本机码 → RemoteManager::Init → JOIN
```

因此，窗口出现后再改本机码可能已经晚于 JOIN；修改输入框也不会自动重新登记。登录按钮始终发送 Login_Info，不能当成完整重连和登录重试入口。

**目标码**则可以等 A 的本机登记成功后在界面填写，因为点击“开始远程”时才读取它。

## 3. 开始前只核对本轮必需的运行条件

### 3.1 地址必须沿生产与消费位置对应

以下端口是当前源码默认值；地址使用本次实际配置，不要求照抄源码中的 IP。监听地址与通告给 Windows 的地址可以因部署映射而不同，但必须实际对应。

| 连接 | 客户端或上游使用的地址来自哪里 | 服务端对应位置 |
| --- | --- | --- |
| A、B → 负载，默认 8523 | LoginWgt 中的负载入口 | [LoadBanceServer/main.cpp](../LoadBanceServer/main.cpp) |
| LoginSvr → 负载，默认 8523 | [LoginServer.cpp](../LoginServer/LoginServer.cpp) | 同一个负载服务 |
| A、B → 登录，默认 9867 | [TcpClient.cpp](../LoginServer/TcpClient.cpp) 上报地址，负载写入 LoginReply | [LoginServer/main.cpp](../LoginServer/main.cpp) |
| A、B → 信令，默认 6539 | [LoginConnection.cpp](../LoginServer/LoginConnection.cpp) 成功分支写入 LoginResult | [SigServer/main.cpp](../SigServer/main.cpp) |
| B 发布、A 拉取，默认 1935 | 客户端 [doCtreatStream](https://github.com/slimesq/ECloudAssistant/blob/main/Net/SigConnection.cpp) 拼出的 RTMP URL | [RtmpServer/main.cpp](../RtmpServer/main.cpp)，同一实例中的同一路径 |

修改服务监听地址，不会自动更新资源上报、登录回复或客户端 URL。确认本次两端代码版本与配置，并核对系统时钟；请求 timestamp 使用 Unix 秒，超时条件复用阶段六。

### 3.2 数据库沿用阶段六，不重新建表

沿用已核对的实验数据库和列序，在数据库客户端中查本轮两名测试用户：

```sql
SELECT USER_CODE, USER_ONLINE
FROM clients
WHERE USER_CODE IN ('345', '346');
```

应能对应到两名合成测试用户，首次进入正常登录分支时在线标记为 0。若只有阶段六准备的 345，复用其显式列插入样例补充 346；已有记录不重复插入，也不重建已有表。

启动 LoginSvr 的进程应继承已设置的 `ENET_DB_PASSWORD`。沿用当前实验实例和连接参数，不把密码写入源码或结果记录。

这里仍有阶段六已确认的限制：查询返回的行指针已失效，在线更新实际使用 INSERT，断线不会自动复位在线标记。配置正确不保证现有登录一定可靠。重试前先查实际状态；只有确认旧会话结束后，才按需恢复本轮专用测试数据。重启程序不等于数据库复位，Destory 也不是退出登录。

### 3.3 采集和输出条件只复用已确认的部分

B 的当前桌面采集区域和编码输入都固定为 `2560×1440`。核对实际采集结果与编码尺寸一致；遇到不匹配时回到客户端阶段六定位，不能只改编码尺寸就认定采集已经适配。

B 需有可用的默认播放设备及短音源；当前采集的不是麦克风。A 使用已能输出画面与声音的运行环境。阶段六至八已有的局部观察直接复用，不再逐项重做示例。

当前推流初始化同时依赖音频和视频。[RtmpPushManager::Open/Init](https://github.com/slimesq/ECloudAssistant/blob/main/Pusher/RtmpPushManager.cpp) 中，音频采集或 AAC 编码初始化失败会直接使 Open 返回 false，尚未调用 OpenUrl，也未创建两个编码发送线程。这不代表此前已启动的底层采集已自动回滚，相关清理复用客户端阶段九。

因此要区分两种情况：

- B 的音频设备不可用等原因导致初始化失败：记录这一步未通过，后续发布、画面与基于播放画面的鼠标验证记为阻断。
- B 已完成采编初始化并发布，只缺少可辨认的音源：声音验证记为阻断，画面与鼠标按实际能运行的部分继续检查；声音条件具备但尚未观察时，才记为待验证。

没有独立桌面时，不能将部分协议观察升级为完整远控效果通过。

## 4. 启动服务和两个客户端

### 4.1 四个服务分别保留前台终端

以下命令在 Linux／WSL 的 ENET 仓库根目录执行，沿用阶段零的 linux-debug 目录；使用其他构建目录时替换相应路径。每个程序单独占一个终端，不要把四条命令依次粘到同一个前台 shell 等待它们自动全部启动。

| 顺序 | 各自终端中的命令 | 进入下一步前确认 |
| --- | --- | --- |
| 1 | `./build/ninja-debug/bin/LoadBanceSvr` | 负载端口确实监听 |
| 2 | `./build/ninja-debug/bin/LoginSvr` | 已连接负载并上报；登录端口也确实监听 |
| 3 | `./build/ninja-debug/bin/SigSvr` | 信令端口监听，本轮登记状态可确认 |
| 4 | `./build/ninja-debug/bin/RtmpSvr` | RTMP 端口监听，准备接收发布与播放 |

前三个入口使用 getchar 保持运行，直接放后台可能因为标准输入结束而提前退出。LoginSvr 在构造时就连接负载，首次连接失败没有完整自动重连，因此先准备负载再启动登录。

资源上报发生在 LoginSvr 开始监听之前，仅看到上报不能代替 9867 已就绪。部分 main 即使 Start 失败也会继续打印 success，不能只看横幅；有疑问时用现有日志、断点或 `ss -ltnp` 核对实际监听。

### 4.2 先 B，后 A，等登记完成再开始控制

1. 启动预配置为 346 的 B，确认登录返回信令地址，服务端实际收到 `JOIN.id=346` 并回复成功。
2. 确认 B 的启动、停止媒体回调已按正常初始化路径绑定，再启动 A。
3. 启动预配置为 345 的 A，确认其本机 `JOIN.id=345` 成功。
4. 在 A 的“远程识别码”输入 346，只点击一次“开始远程”。B 不点击开始远程。

MainWgt 默认可以显示远程页面，页面出现不表示登录或 JOIN 已成功。客户端是 GUI 程序，也不一定附带控制台；观察可使用已有调试输出和服务端日志，不要求先新增日志系统。

若初始化连接失败，先定位并恢复条件。准备重新启动实例前，还需确认旧信令登记是否释放；不要把重复点击按钮当成可靠恢复流程。

## 5. 正常会话：先确认同一条交互，再看实际效果

### 5.1 只跟这一轮的三个信令连接与同一 URL

| 观察点 | 本轮应看到什么 | 两端关键入口 |
| --- | --- | --- |
| 本机登记 | A=345、B=346 均已登记 | 客户端 RemoteManager::Init；服务端 HandleJion |
| 控制登记与获取目标 | A 另建控制连接 JOIN(154564)，成功后请求目标 346 | 客户端 doJoin/obtainStream；服务端 DoObtainStream |
| 目标空闲分支 | 服务端建立关联，保存控制连接的 conn_=B，通知 B 建流 | 服务端 SigConnection |
| B 启动与回复地址 | 真正进入推流启动函数，回复本轮 URL | doCtreatStream → RemoteManager::HandleStartStream → RtmpPushManager::Open |
| A 收到播放通知 | PLAYSTREAM 携带同一 URL，进入读流入口 | DoCreateStream → doPlayStream → AVPlayer::HandleStartStream → AVDEMuxer |

上述 conn_ 是**服务端连接对象**的成员。A 的本机登记连接和控制连接是两条 TCP，不能用 345 代替本轮控制连接的 154564。

本轮应从目标空闲分支开始。若 B 已经处于 PUSHER，先确认是否有上一轮残留；已有流分支遗漏输入目标赋值，不能将它与正常首次建流混在一起解释。

客户端 SigConnection 的默认媒体启动回调直接返回 true，外层在构造连接之后才绑定实际推流回调；若收到建流成功回复却没有媒体连接，要检查是否真的进入了 HandleStartStream，而不只是看回调是否非空。信令成功、OpenUrl 返回、RTMP 发布接受与首帧是不同层次，判断沿用阶段十。

### 5.2 画面、声音和鼠标各看实际结果

| 项目 | 本轮操作 | 足以支持通过的结果 |
| --- | --- | --- |
| 画面 | 在 B 显示文本窗口并移动窗口或改变可见内容 | A 显示的是 B 的内容，变化能持续传来，而不是只有一次静止图像 |
| 声音 | B 在默认播放设备播放一段已有短音频或提示音，再停止音源 | A 实际听到对应声音，声音变化能与 B 的操作对应 |
| 鼠标 | 在 A 的播放画面有效区域内移动鼠标，并在画面中 B 文本窗口对应的位置，通过 A 的鼠标做一次按下/释放 | B 的实际光标位置或窗口焦点按操作变化，鼠标按键释放后没有持续按住的现象 |

沿第 2 节确保 A 的回放不进入 B 正在采集的播放设备。耳机可用于听取 A 的输出，但不能代替这项隔离；WASAPI loopback 采集的是设备播放数据，换耳机并不会排除同设备的回放。没有音源时的安静不能直接当成声音失败，先确认 B 确有系统播放声音。

鼠标通过只覆盖本次移动与点击；键盘释放、特殊键、组合键与多种 DPI 不在最小主线内。若本轮主动选择键盘，还要观察释放，不能只凭出现一个字符判断通过。

### 5.3 出现黑屏、无声或输入无效时从哪一层继续

只追最早未成立的交接点：

```text
信令与 URL
  → B 真正启动采编与发布
  → 发布方收到 NetStream.Publish.Start
  → 服务端同一实例、同一 path 的 Session 收到并分发媒体
  → A 的 FFmpeg 打开输入、取得 Packet
  → 解码、画面与声音实际输出

鼠标另看：
A 事件 → SigSvr 的 conn_ 目标与转发 → B 的 doMouse*Event → 实际桌面响应
```

当前 AAC 配置走错 type 9、固定采编尺寸、半包处理及异步失败反馈等问题，已经在前序讲义定位。若本轮已进入某一步却得到错误结果、卡住或崩溃，该步记为未通过；因此尚未进入的后续步骤记为阻断。不要求开始前先修完全部问题，画面通过也不能代替声音通过，发布日志更不能代替实际输出。

## 6. 正常退出：窗口、线程、连接分别确认

### 6.1 先关 A 的播放窗，再退出 A，最后退出 B

1. 关闭 A 的远程播放窗口，保留 A 主窗口，观察播放和网络是否真的停止。
2. 再通过 A 主窗口的关闭按钮请求退出，观察主事件循环是否返回、关闭与析构是否进入、相关线程是否结束以及进程是否退出。
3. 同时保留服务端运行，观察 A 的控制连接和媒体播放连接是否清理；B 是否收到停止通知、是否仍在采编。
4. 请求 B 主窗口退出，继续确认其采编线程、发布连接、本机信令连接及服务端会话清理。

这是一组**待验证的正常退出操作**，不是当前源码已经保证完成的结果。先隐藏播放窗，可避免它作为仍可见的独立顶层窗口干扰“最后一个窗口关闭”的判断。

### 6.2 每一层用什么证据判断

| 层次 | 本轮确认什么 | 当前容易误判的地方 |
| --- | --- | --- |
| 播放窗口 | 是否实际进入 AVPlayer::Close，而不只是不再可见 | PullerWgt 当前没有将关闭事件接到播放器停止，也未设置关闭即删除，通常只隐藏 |
| A、B 的工作线程 | 停止入口与相应 join/wait 是否完成 | 设置标志或看不到画面，不等于线程已结束 |
| 信令连接 | Close/Clear、登记移除和关联变化是否发生 | ENET 没有为 recv==0 单独关闭，不能预设 A 断开就一定通知 B 停推 |
| 媒体连接与 Session | 是否进入 OnClose、延迟 RemoveSink，之后空会话是否移出表 | 1 毫秒、3 秒是调度间隔，不是清理完成保证 |
| 对象与 fd | 持有者是否释放、析构与 socket close 是否发生 | 逻辑 Close 不直接释放 fd，进程终止后的系统回收不能证明这条链 |

关闭细节直接复用两端关闭讲义。已请求退出，却卡在停止等待、空线程指针、裸回调或服务端清理等位置时，退出步骤记为未通过；因此尚未进入的后续检查记为阻断。前面已经实测通过的部分仍然保留。

A 退出后若 B 仍发布，先记录这一事实，再单独请求 B 退出；不要把 B 的手动退出写成“A 断开后自动停推已通过”。

## 7. 一个简单失败：目标不存在

若本轮已实际遇到并能清楚定位一个简单失败，可直接复用，不必再额外制造。下面给出补做时的固定步骤；它与正常会话分开，不在已经使用过的控制窗口中改码重试。

### 7.1 先清理上一轮状态，再启动本轮新 A

1. 确认旧 A 已结束，并确认信令服务中本机码 345、控制注册码 154564 均未被旧连接占用。仅重启 A，不能保证旧登记已消失。
2. 若有残留，先重置本次专用的既有 SigSvr 进程，再核对本轮测试用户状态；环境准备完成后才启动新 A。客户端没有可靠的自动重连流程，不能让已连接旧服务的 A 直接接着测试。
3. 启动全新 A，确认登录和本机 JOIN 成功，再选一个确实未登记、且不等于 A 本机码的短码，例如 999999。

本项不需要重新启动 B、采集或发布，先前正常会话的结果直接保留。若旧 A 退出卡住或崩溃，该退出结果仍记未通过；随后强制终止进程只是环境清理，不改成正常退出通过。无法确认本例前置时，记本例阻断，不反复点击。

### 7.2 只发起一次，再核对拒绝与客户端表现

1. A 本机 JOIN 成功后，在目标框填 999999，只点击一次“开始远程”。
2. 确认 A 的控制 JOIN(154564) 成功，服务端收到 `OBTAINSTREAM.id=999999`。
3. 在 [DoObtainStream](../SigServer/SigConnection.cpp) 确认查找为空，返回 `OBTAINSTREAM` 消息中的 `result=ERROR(1)`，没有创建目标关联或发出 CREATESTREAM。
4. 在 A 核对错误回复是否到达，以及界面和本地状态是否处理它，到此结束本轮。

这里是 OBTAINSTREAM 的 result 字段为 1，不是负载错误使用的 cmd=ERROR。若实际停在重复 JOIN、登录失败或连接失败，说明尚未进入目标不存在分支，不能记该例通过。

当前客户端没有 OBTAINSTREAM 回复的业务处理分支：消息可能已接收并从缓冲消费，但不会自动提示目标不存在或把本地 PULLER 恢复为空闲。因此应分别记录：

- 服务端拒绝正确、没有通知建流：这一处理可以通过。
- 客户端没有错误反馈和状态恢复：这部分未通过，不能因服务端拒绝正确就合并写成完整失败处理通过。

### 7.3 不将失败后的重试和恢复列为额外任务

失败窗口尚未开始播放时，audioThread_/videoThread_ 可能还没创建，当前 AVPlayer::Close 却先解引用它们。再次“开始远程”会替换旧窗口并触发销毁，可能先在清理处出错；仅关闭窗口又可能只隐藏它，旧控制登记也可能保留。

因此本例观察完就结束，不在原窗口反复改目标、重新开始。若随后退出卡住或崩溃，单列为失败后的清理问题；确需终止实验进程时记为清理动作，不能补写成正常退出通过。

## 8. 最后结束服务，区分正常入口与环境清理

全部客户端结束后，再使用现有服务入口退出。保留服务端终端和调试信息，先记录客户端退出后的连接、登记与 Session 状态，再结束进程。

- LoadBanceSvr、LoginSvr、SigSvr 的前台终端可按 Enter，使 getchar 返回；之后继续观察 Stop、析构和 EventLoop::Quit/join 是否真的完成。
- LoginSvr 先于 LoadBanceSvr 退出，避免负载已结束后登录服务还在周期上报；SigSvr 在相关客户端都已结束后退出。
- RtmpSvr 的当前 main 是无限 sleep，没有现成正常退出入口。未修改入口时，这项正常停机保持阻断；Ctrl+C、调试器终止或强制结束只能用于实验清理。
- 其他服务若在 Stop 遍历、回调或线程等待中卡住，也按实际结果记录，不以终端消失或进程被结束代替正常停机证据。

前序已经得到的同版本退出结果可复用；本轮只验证尚未确认或已变化的部分。
