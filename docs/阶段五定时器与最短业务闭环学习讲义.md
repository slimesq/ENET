# ENET 阶段五：定时器与最短业务闭环学习讲义

> 对应[项目学习规划的阶段五](项目学习规划.md#stage-5)。参考用时：4～6 小时，基础补学、环境配置和排障另计。
>
> 跟踪两条现有路径：一条请求怎样得到回显，一个定时回调怎样注册、到期、重复或移除。复用阶段二至四的协议、调度和缓冲知识，重点看路径之间怎样衔接。

## 1. 学习顺序与必要概念

按以下顺序学习：

2. 核对两个索引表及 `AddTimer → HandleTimerEvent → RemoveTimer` 的关系。
3. 用固定时间线解释回调返回值和下一次到期时间。
4. 沿现有 echo 代码连接接入、读取、业务回调、发送和关闭。
5. 按需运行现有 TimerQueue 的短片段；已有服务可运行时，再观察一个实际定时回调。

### 1.1 时间间隔、到期和执行分别是什么

| 概念 | 本项目中的含义 |
| --- | --- |
| 间隔 `interval_` | 注册时传入的毫秒数，源码形参拼写为 `mesc` |
| 到期时刻 `next_timeout_` | 同一时钟域中的一个时间值，用来判断何时可以执行 |
| 扫描时刻 | `HandleTimerEvent()` 本轮开始时取得的时间快照 |
| 实际执行时刻 | 调度线程真正进入回调的时刻，可能晚于到期时刻 |

到期不等于立即执行。工作线程还可能正在处理其他回调，只有再次检查定时器时，才能发现已到期任务。

### 1.2 单调时钟与登录时间戳用途不同

`TimerQueue::GetTimeNow()` 使用 `steady_clock`，转换为毫秒计数。单调时钟适合计算间隔，时间值不会因校准系统日期而倒退，见 [steady_clock 的定义](https://eel.is/c++draft/time.clock.steady)。

当前 Linux 环境中的登录超时判断则使用 `system_clock` 的秒计数，按 Unix 时间戳与请求中的 `timestamp` 比较。`system_clock` 表示系统日期时间，见 [system_clock 的定义](https://eel.is/c++draft/time.clock.system)。

这两处不仅单位不同，时钟起点和用途也不同。不能把定时器的单调毫秒值直接写进登录请求的 Unix 秒时间戳字段，或将两者直接相减。

## 2. 一个 Timer 为什么有两个索引

### 2.1 Timer 保存任务，TimerQueue 负责管理

`Timer` 保存间隔、下一次到期时刻和回调 `evenrt_callbak_`。回调类型是 `std::function<bool(void)>`，返回值由队列解释。

`TimerQueue` 使用两个表：

```cpp
std::unordered_map<TimerId, std::shared_ptr<Timer>> timers_;
std::map<std::pair<int64_t, TimerId>, std::shared_ptr<Timer>> events_;
```

| 表 | 键 | 作用 |
| --- | --- | --- |
| `timers_` | `TimerId` | 根据 ID 找到任务，供取消等操作使用 |
| `events_` | `(到期时刻, TimerId)` | 按到期时间排序，从 `begin()` 找最早的任务 |

两表保存指向同一个 Timer 的共享指针，不是复制两份独立任务。时间相同的两个任务，例如 `(1100, 1)` 与 `(1100, 2)`，仍有不同的键；默认排序会先比较时间，再比较 ID。

### 2.2 AddTimer 设置了哪些值

[TimerQueue::AddTimer()](../EdoyunNet/Timer.cpp) 的顺序是：

```text
取得当前单调毫秒值 t0
  → 本队列生成一个 TimerId
  → 创建 Timer，保存回调和间隔
  → SetNextTimeOut(t0)
  → timers_[id] 保存任务
  → events_[(t0 + interval, id)] 保存同一任务
  → 返回 id
```

名字 `SetNextTimeOut(t)` 容易让人误以为直接保存 t；实际实现是：

```cpp
next_timeout_ = time_point + interval_;
```

因此，若在 1000 毫秒添加间隔为 100 毫秒的任务，Timer 保存的到期时间为 1100，事件表中的键为 `(1100, id)`。

`Timer::Sleep()` 只是 `sleep_for` 的包装。TimerQueue 不靠它自动等待或启动线程，回调执行依赖外层主动调用 `HandleTimerEvent()`。

## 3. 到期后怎样执行、重复或结束

### 3.1 调度器每轮先扫描定时器

服务中的调用路径是：

```text
调度工作线程
  → TaskScheduler::Start
  → TimerQueue::HandleTimerEvent
  → 执行本轮已到期的回调
  → 再进入 I/O 事件处理
```

这些回调在所属调度器线程同步执行，不会自动另建线程。慢回调会推迟同一线程上的其他定时器和网络事件，线程结构复用[阶段三](阶段三epoll与事件循环学习讲义.md)。

`HandleTimerEvent()` 在入口只读取一次时间快照。扫描最早事件时：

| 条件或返回值 | 当前处理 |
| --- | --- |
| 最早任务还没有到期 | 结束本轮到期扫描 |
| 任务已到期 | 执行该任务的回调 |
| 回调返回 true | 保留任务，按本轮时间快照加间隔，重新排入事件表 |
| 回调返回 false | 从 `events_` 与 `timers_` 都移除该任务 |

这里的 true/false 表示继续安排或结束任务，不表示业务成功或失败；即使本次业务失败，回调也可以根据自己的逻辑返回 true，等待下一次执行。

### 3.2 用固定时间线推导下一次到期

以下假定串行操作一个任务，时间值都属于同一个单调时钟域：

| 时刻或动作 | 结果 |
| --- | --- |
| 1000 毫秒注册，间隔 100 毫秒 | 首次到期时间为 1100 |
| 1099 毫秒扫描 | 未到期，不执行 |
| 1140 毫秒进入 `HandleTimerEvent()` | 本轮快照为 1140，任务已到期 |
| 回调执行 30 毫秒，1170 毫秒返回 true | 下一次到期时间设为 `1140 + 100 = 1240` |
| 此后回调返回 false | 移除任务，不再重复 |

下一次到期时间不是旧到期时刻加间隔得到的 1200，也不是回调结束时刻加间隔得到的 1270。当前实现使用的是**本轮扫描快照加间隔**。

若这次回调耗时很长，实际结束时刻已经超过 1240，下一轮扫描可能很快再次发现任务到期。本轮扫描仍使用 1140 的快照，不会因回调期间真实时间继续前进，就在同一轮逐次追补原来的时间线。

所以“间隔 100 毫秒”描述的是当前安排规则，不保证每次都准确相隔 100 毫秒执行。以下示例均使用正间隔；重复任务若用 0 间隔，当前实现会将它排回同一时刻，可能在本轮持续执行。

## 4. 取消、线程与捕获对象怎样对应

### 4.1 取消要同时删除两个索引

[TimerQueue::RemoveTimer()](../EdoyunNet/Timer.cpp) 根据 ID 找到 Timer，取出其当前到期时间：

```text
timers_ 查找 id
  → events_ 删除 (当前 next_timeout_, id)
  → timers_ 删除 id
```

重复任务重排时，Timer 内的到期时间与事件表的键会一起更新。因此，正常串行路径中取消使用的是当前键，不是最初注册时的旧键。找不到 ID 时，该函数不做操作，也不返回是否取消成功。

移除两表的引用后，Timer 及其回调保存的对象何时释放，取决于是否还有其他所有者。

### 4.2 ID 必须交回所属队列

每个 TimerQueue 都有自己的 ID 计数器，TimerId 不包含队列身份，也不是全进程唯一标识。

真实接口拼写是：

```text
EventLoop::RemvoTimer
  → TaskScheduler::RemvoTimer
  → TimerQueue::RemoveTimer
```

通过 `EventLoop::AddTimer()` 注册的任务属于 0 号调度器，对应的 `EventLoop::RemvoTimer()` 也转发到 0 号。直接通过某个调度器注册的任务，则应交回那个调度器取消，不能只拿一个 ID 就假定 EventLoop 能找到它。

### 4.3 当前取消与存活还有哪些条件

TimerQueue 的添加、取消和扫描没有内部锁；EventLoop 只是直接转发调用，没有自动将这些操作投递到工作线程。实际服务在主线程构造时注册任务，而工作线程已经运行，相关同步需要检查。

回调捕获 `[this]` 不延长服务对象寿命。取消也没有“等待正在执行的回调结束”的协议，不能仅凭调用删除接口就认定对象可以立即销毁。

当前扫描代码在回调返回后还会继续访问 `events_.begin()`。回调若直接删除自身，可能改变或清空正在处理的事件表；简单任务用返回 false 表示结束，不能把回调内自取消当成已经安全支持的能力。

本阶段认清这些条件即可，跨线程取消、回调重入和完整停机顺序留[阶段十一](项目学习规划.md#stage-11)检查。

## 5. 跟一条现有请求响应路径

### 5.1 哪个演示真正实现了回显

| 代码 | 当前用途与构建状态 |
| --- | --- |
| [EdoyunNet/main.cpp](../EdoyunNet/main.cpp) | 创建基础 TcpServer；没有安装回显业务回调，且被网络库构建排除 |
| [TCPServer/mian.cpp](../TCPServer/mian.cpp) | 创建 EchoServer；顶层 CMake 没有加入该子目录，不是默认运行目标 |
| [EchoServer::OnConnect](../TCPServer/EchoServer.cpp) | 创建 LConnection |
| [LConnection::HandleMessage](../TCPServer/LConnection.cpp) | 读取当前可读区并回传这些字节 |

入口文件确实拼写为 `mian.cpp`。`TCPServer/CMakeLists.txt` 定义了 `TCPSvr`，但顶层没有纳入它，因此默认构建后不能直接假定存在该程序。

### 5.2 接收怎样得到回显

跟踪已有代码：

```text
客户端连接
  → EchoServer::OnConnect 创建 LConnection
  → 安装读取业务回调
  → 连接读就绪
  → TcpConnection::HandleRead → BufferReader::Read
  → LConnection::OnRead → HandleMessage
  → ReadAll(str)
  → Send(str.c_str(), str.size())
  → 本地写队列与 socket
  → 客户端接收回显
```

`LConnection::HandleMessage()` 的关键语句是：

```cpp
std::string str;
buffer.ReadAll(str);
printf("data: %s\n", str.c_str());
Send(str.c_str(), str.size());
buffer.RetrieveAll();
```

`ReadAll` 已复制当前可读字节并清零索引，最后再调用 `RetrieveAll()` 是重复清零。

例如，假定这次已经读入四个字节 `50 49 4E 47`，即 `PING`，`ReadAll` 得到长度为 4 的字符串，复制版 `Send` 提交 4 字节回显。若本次收到的是 `41 00 42`，字符串长度和回显长度都是 3，但 `printf("%s")` 遇零会停止显示，不能用这一行日志代替字节长度检查。

回显按当前可读区处理，不按行或完整业务消息分包。请求可能分次到达，回显也可能分次接收；字节流边界仍按阶段二理解，复制和发送完成含义复用[阶段四](阶段四TCP连接收发缓冲区与背压学习讲义.md)。

### 5.3 初始发送与关闭位置

LConnection 构造时会先发送一段预置文本，使用 `sizeof(buf)`，包含末尾零。若运行这个演示，第一次收到的数据可能先是这段文本，也可能与后续回显合并，需要按实际字节区分。

`TcpConnection` 构造函数中另有一个发送 `"this is server.\n"` 的定时任务，但注册调用被注释，不会自动定时发送。

连接结束时，仍要区分：

```text
TcpConnection::Close 标记关闭
  → 从调度器移除 Channel
  → 若设置了业务 closeCb_，执行该回调
  → disconnectCb_ 使 TcpServer 移除连接表项
  → 最后一个连接所有者释放后，析构中关闭 fd
```

LConnection 没有设置自己的业务关闭回调，不能把该步骤画成它必经的业务处理。此处只定位各步骤，具体 EOF、错误处理及当前析构条件继续对照阶段四，完整时序留阶段十一。

## 6. 服务中一个真实的定时回调

### 6.1 RtmpServer 的重复清理

[RtmpServer 构造函数](../RtmpServer/RtmpServer.cpp)通过 `EventLoop::AddTimer(..., 3000)` 注册清理回调：

```text
构造 RtmpServer
  → 添加到 0 号调度器的 TimerQueue
  → 到期扫描时检查会话表
  → 清理没有客户端的会话
  → 返回 true，重新安排
```

本阶段只看定时器接口、调用线程和返回值，不展开 RTMP 协议。即使会话表为空，这个回调也会被安排；回调没有打印语句，不能以“没有每三秒的控制台输出”判断它没有执行。

已有服务可运行时，可在这个 lambda 中设断点，确认它由 0 号调度工作线程调用。源码没有保存这次注册返回的 TimerId，析构函数也没有取消它，不能据此认为服务退出时已完成安全取消。

### 6.2 登录上报只作条件对照

[LoginServer 构造函数](../LoginServer/LoginServer.cpp)只有在连接负载服务成功后，才会：

1. 立即调用一次 `getMonitorInfo()`；
2. 注册间隔为 1000 毫秒、返回 true 的回调。

第一次立即上报不是定时器提前触发。后续上报才来自定时器，资源信息与负载业务在阶段六学习。本阶段读清条件即可，无需为观察定时器先完成数据库或启动整条登录业务。

## 7. 按需直接观察现有 TimerQueue

若时间和回调规则已清楚，可直接进入自检。需要代码观察时，在 **Linux／WSL 终端的仓库根目录**运行以下片段。它直接使用仓库的 TimerQueue，不启动网络服务，也不修改构建配置。

```sh
timerDir="$(mktemp -d)"
c++ -std=c++17 -pthread -I. -x c++ - EdoyunNet/Timer.cpp -o "$timerDir/EnetTimerExample" <<'CPP'
#include "EdoyunNet/Timer.h"
#include <cstdio>

int main()
{
    TimerQueue queue{};
    int ticks{};
    bool cancelledRan{};
    const TimerId cancelledId{queue.AddTimer([&cancelledRan]() {
        cancelledRan = true;
        return false;
    }, 20)};
    queue.RemoveTimer(cancelledId);

    queue.AddTimer([&ticks]() {
        ++ticks;
        std::printf("tick=%d\n", ticks);
        return ticks < 2;
    }, 20);

    for (int round{}; round < 2; ++round)
    {
        std::this_thread::sleep_for(std::chrono::milliseconds{30});
        queue.HandleTimerEvent();
    }
    std::printf("ticks=%d cancelled=%d\n", ticks,
        static_cast<int>(cancelledRan));
    return ticks == 2 && !cancelledRan ? 0 : 1;
}
CPP
"$timerDir/EnetTimerExample"
```

应看到：

```text
tick=1
tick=2
ticks=2 cancelled=0
```

第一项在扫描前取消，故不会执行。第二项第一次返回 true，第二次返回 false，随后从两表移除。这里的间隔是 20 毫秒，而扫描前等待 30 毫秒，是为了在每次扫描时已有到期任务，不是在验证精确的 20 毫秒周期。

片段由主线程主动调用 `HandleTimerEvent()`，因此回调也在主线程执行；服务中的调用者则是 TaskScheduler 工作线程。该片段没有跨线程访问队列，不能用它证明实际服务的并发操作已经安全。

已有可运行的 EchoServer 演示时，可用它观察网络回显；使用其他已能运行的服务时，只观察该服务现有的请求响应路径。Echo 演示的固定地址需要属于本机，6539 端口还要与信令服务错开。没有现成运行条件时，先完成第五节的源码与字节推演，后续再补一次观察。
