> 对应[项目学习规划的阶段十](项目学习规划.md#stage-10)。参考用时：2～4 小时。
>
> 从服务端入口出发，沿“接收什么 → 读取哪些字段 → 保存什么关系 → 回复或转发给谁 → 客户端怎样消费”对照。复用已有协议、信令和媒体知识，动态跨端验收统一放在阶段十二。

## 1. 学习顺序与源码入口

本阶段在客户端阶段零至九之后进行。C++、socket 和事件循环基础直接复用；Qt、Windows 输入和编解码内部已有客户端讲义，本阶段只定位它们与服务端的交接位置。

建议顺序：

1. 先分清负载、登录、信令和媒体分别使用哪条连接。
2. 从服务端处理函数反查请求生产方，再顺着回复找到客户端消费方。
3. 跟一次正常建流，核对目标不存在、已有流和停止时的差异。
4. 将同一媒体 URL 对到发布、会话和播放入口，再跟一条输入消息。
5. 核对地址来源，区分源码结论与阶段十二需要实测的结果。

## 2. 先按连接与协议区分消息

### 2.1 服务端面对的不只是一条客户端连接

| 连接用途 | 发起方与服务端 | 承载消息与用途 |
| --- | --- | --- |
| 查询登录入口 | GUI 客户端 LoginWgt → LoadBanceSvr | 接收 Login_Info，回复登录服务地址 |
| 登录 | LoginWgt → LoginSvr | 接收 UserLogin，成功时回复信令地址 |
| 资源上报 | LoginSvr 的 TcpClient → LoadBanceSvr | 接收 Monitor_body，更新登录服务信息 |
| 本机信令登记 | RemoteManager::Init → SigSvr | CONTROLLED 连接以本机码 JOIN，接收建流通知和远程输入 |
| 主动控制目标 | AVPlayer::Connect → SigSvr | 另建 CONTROLLING 连接，JOIN 后请求目标，并发送输入 |
| 媒体发布 | RtmpPublisher::OpenUrl → RtmpSvr | 发布侧自定义 RTMP 客户端发送命令、配置和编码数据 |
| 媒体播放 | AVDEMuxer 的 FFmpeg 输入 → RtmpSvr | 独立播放连接请求同一路径，服务端分发媒体 |

客户端使用同一个 QTcpSocket 对象从负载地址切换到登录地址，也会产生新的 TCP 连接。本机信令、控制信令、媒体发布和媒体播放同样应分别跟踪，不能把同一进程里的消息都归到一条连接。

### 2.2 自定义消息与 RTMP 分开阅读

负载、登录和信令使用项目结构体，公共包头为 `len:uint16_t + cmd:uint16_t`，共 4 字节，len 包含包头。当前使用 pack(1) 和直接内存发送，没有统一逐字段转成网络大端。下面的长度沿用当前两端布局，其中结果字段按 4 字节计算；结构体同名或总长相同，也不能代替字段偏移核对。

RTMP 使用自己的握手、Chunk、Message 和 AMF。信令的 `CREATESTREAM/PLAYSTREAM` 与 RTMP 的 `createStream/play` 属于不同协议：

- 信令决定通知哪个客户端启动、把哪个 URL 交给控制方。
- RTMP 决定媒体连接的发布或播放角色，并实际承载编码数据。
- 输入仍走信令 TCP，不随 RTMP 视频帧传输。

对照时始终先确定“哪个服务、哪个方向、哪个步骤”，再解释命令值与包体。

## 3. 负载与登录：从服务端字段读到客户端下一步

### 3.1 四种正常报文都使用 Login 命令

| 方向与报文 | 当前总长 | 服务端实际动作 | 客户端生产或消费位置 |
| --- | --- | --- | --- |
| 客户端 → 负载：Login_Info | 12 字节 | `HnadleLogin` 读取 timestamp，检查请求时间，查询资源记录 | LoginWgt 构造时自动发送，按钮回调也发送此报文 |
| 负载 → 客户端：LoginReply | 22 字节 | 将选出的登录服务 port、ip 写入回复 | `HandleLogin` 的 `is_login_=false` 分支 → `HandleLoadLogin`，切换到登录服务 |
| 客户端 → 登录：UserLogin | 77 字节 | `HandleLogin` 检查 timestamp，按 code 查询用户及在线标记 | `HandleLoadLogin` 在连接登录服务后填写 code、count、passwd、timestamp |
| 登录 → 客户端：LoginResult | 26 字节 | 写 resultCode，成功分支填写信令 port、ctrSvrIp | `HandleLogin` 的 `is_login_=true` 分支，成功时发出 sig_logined |

四种正常报文都是 `cmd=Login(2)`。客户端用 `is_login_` 选择两种响应布局；它在登录服务 TCP 连接成功后就被设为 true，表示当前登录步骤，不表示已经认证成功。

服务端当前按 `code → USER_CODE` 查询，没有比较请求中的 count/passwd。客户端登录 code 固定设置为 `"345"`，账号与密码来自输入框。因此不能把 `S_OK` 解释为“已完成账号密码校验”。

字符数组的长度、填充和结束符问题继续复用阶段二、六的结论。源码中调用 `SetCode("345")`，不等于接收端一定能安全地按以零结尾的字符串读取它。

### 3.2 登录地址和信令地址由不同位置生产

```text
LoginSvr::TcpClient 填 Monitor_body.ip/port
  → LoadBanceConnection::HandleMinoterInfo
  → LoadBanceServer::UpdateMonitor / GetMonitorInfo
  → HnadleLogin 填 LoginReply
  → 客户端 HandleLoadLogin 连接登录服务

LoginConnection::HandleLogin 成功分支填信令地址
  → LoginResult
  → 客户端 sig_logined
  → RemoteWgt::handleLogined → RemoteManager::Init
```

`Monitor_body` 是服务之间的上报，不是用户登录请求。LoginResult 的信令地址当前在 LoginConnection 中填写，并未从数据库的服务器挂载字段动态选择。

### 3.3 错误回复也要找到真实消费者

| 情况 | 服务端怎样表示 | 客户端当前处理 |
| --- | --- | --- |
| 负载请求超时或服务对象失效 | 将 LoginReply.cmd 改为 `ERROR(1)` | `ERROR_ → HandleError`，当前只打印日志 |
| 登录超时、查不到用户或已在线 | 仍为 Login 命令，用 resultCode 区分 | 只处理成功结果，失败分支没有完整反馈 |
| 没有登录服务资源记录 | `GetMonitorInfo` 直接访问首元素，缺少空集合保护 | 此路径没有可靠的空集合错误回复 |

登录按钮始终发 Login_Info，不能把它视作切换地址后完整重发 UserLogin 的重试入口。

`Register` 在服务端尝试入库后回复 RegisterResult，但插入结果没有完整传回，成功码不能证明实际写入成功。`Destory` 是按 code 删除用户记录，没有对应业务回复，不能当作退出登录或在线状态复位。客户端注册处理函数为空，也没有接通这两项的发送流程；本阶段只定位这些边界。

资源记录借用接收缓冲、数据库行指针失效及在线更新实际使用 INSERT 等问题，沿用阶段六的分析，不在这里重做数据库实验。

## 4. 信令：把字段、连接关系和客户端回调对应起来

### 4.1 服务端保存的几种关系

| 标识或成员 | 来自哪里 | 服务端用途 |
| --- | --- | --- |
| UserLogin.code | 客户端登录消息 | 查询数据库，不会自动变成 JOIN 登记 |
| JOIN.id → code_ | 每条信令连接的登记消息 | ConnectionManager 以此查找连接 |
| OBTAINSTREAM.id | 控制方填写的目标识别码 | 查找被控连接 |
| objectes_ | 建立远控关联时互相登记 | 保存关联识别码，供通知和移除使用 |
| conn_ | 正常获取空闲目标时赋值 | 控制连接保存输入转发目标 |
| streamAddres_ | 被控方 CREATESTREAM 回复 | 保存媒体 URL，供 PLAYSTREAM 通知使用 |

客户端的 CONTROLLED/CONTROLLING 角色没有作为独立字段传给服务端。服务端根据 JOIN、获取流等交互更新自己的状态；两端本地状态枚举数值不要求相同，因为它们没有直接在线上传输。

本机识别码、目标识别码和控制连接自己的 JOIN.id 是三个位置。当前控制连接 JOIN.id 固定为 `"154564"`；媒体流名则来自客户端进程内计数器，既不是这个注册码，也不是目标识别码。

### 4.2 每条信令由谁生产、谁消费

| 消息与当前长度 | 服务端读取、修改或发送 | 客户端对应入口 |
| --- | --- | --- |
| JOIN(5)：请求 14，回复 8 字节 | `HandleJion` 读 id；检查重复，成功后登记 code_、置 IDLE，回复 result | `Join` 生产，`doJoin` 消费回复；控制连接成功后发获取流请求 |
| OBTAINSTREAM(6)：请求 14，回复 8 字节 | `DoObtainStream` 读目标 id，查询状态并建立关联或返回错误 | `obtainStream` 生产；客户端分发器没有消费该回复的分支 |
| CREATESTREAM(7)：通知 4，回复 78 字节 | 向被控方发纯包头通知；`DoCreateStream` 从回复读取 streamAddres | `doCtreatStream` 生成 URL、调用启动回调，回复 result 和 URL |
| PLAYSTREAM(8)：通知 78 字节 | 向控制方发 result 和 streamAddres | `doPlayStream` 调用播放器回调，进入 `AVPlayer::HandleStartStream` |
| DELETESTREAM(9)：当前消息体声明对应总长 8 字节 | 收到时只在忙碌状态调用 Clear，不读取 streamCount；Clear 向关联方发通知 | `doDeleteStream` 读取 streamCount，等于 0 时调用停止回调 |

信令结果字段中，成功值 0 在服务端叫 `SUCCESSFUL`，在客户端叫 `S_OK_`；失败值 1 分别叫 `ERROR`、`SERVER_ERROR`。两端按数值对应。这里的 result 与负载错误回复的 `cmd=ERROR(1)` 是不同字段，不能只看到数值 1 就按同一消息解释。

CREATESTREAM 回复虽然有 result 字段，服务端当前没有检查它，主要按地址是否为空及关联状态继续处理。服务端没有等待或核实 RTMP 发布成功，PLAYSTREAM 在此只负责转交媒体地址和信令结果。

源码中有 PLAYSTREAM 回复结构体声明，但当前客户端没有相应业务回复，服务端 switch 也没有消费该回复的分支。声明存在，不代表一轮交互已经实现。

### 4.3 用两个客户端跟一轮正常建流

以 A 控制 B 为例，假定两端按预期绑定了推流和播放回调，信令登记成功且目标空闲：

```text
A 本机登记连接 JOIN(345)；B 本机登记连接 JOIN(346)
A 另建控制连接 JOIN(154564)
  → JOIN 成功后发 OBTAINSTREAM(id=346)
  → 服务端查到 B 本机登记连接对应的对象
  → 在服务端，A 控制连接对象与 B 登记连接对象互记 objectes_
  → 服务端的 A 控制连接对象置 PULLER，保存 conn_=服务端的 B 登记连接对象
  → 向 B 发 CREATESTREAM；向 A 控制连接发 OBTAINSTREAM 成功回复
B 的 doCtreatStream 拼 URL，调用 RemoteManager::HandleStartStream
  → RtmpPushManager::Open → RtmpPublisher::OpenUrl
  → B 回复 CREATESTREAM(result, URL)
服务端 DoCreateStream 保存非空 URL，将 B 的信令连接对象置 PUSHER
  → 向关联的 A 控制连接（JOIN.id=154564）发 PLAYSTREAM(result, URL)
A 的 doPlayStream → AVPlayer::HandleStartStream → AVDEMuxer::Open
```

上面的 objectes_、conn_ 和状态赋值属于服务端 SigConnection。客户端有自己的本地状态，不能将两端对象视作同一对象。这里的 345、346 是解释登记关系的例子，不代表登录已将这些码认证或绑定。两台客户端若都使用固定控制注册码，同时主动控制时还可能在 JOIN 处冲突。

被控方的启动回调返回值只是这一步的本地调用结果。RTMP 发布应答和首个可播放帧，仍要分别沿媒体连接核对。

## 5. 三种分支：目标不存在、已有流与停止

### 5.1 目标不存在

服务端回复 OBTAINSTREAM(ERROR)，不创建关联，也不向任何目标发 CREATESTREAM。客户端在发送获取流请求后已将本地状态设为 PULLER，又没有处理 OBTAINSTREAM 回复，因此不能预期它自动恢复空闲或显示“目标不存在”。

这条路径适合在阶段十二作为简单失败观察；本阶段先从两端分发器确认处理缺口。

### 5.2 目标已有流地址

目标处于 PUSHER 且地址非空时，服务端建立关联，直接向新控制方发送 PLAYSTREAM，不再通知被控方创建流，也没有另发 OBTAINSTREAM 成功回复。

这一分支遗漏了 `conn_=目标连接`。媒体 URL 已经发出，不代表输入转发目标已经保存，因此可能出现“可以尝试播放，但输入没有被转发”的情况。定位时分别核对 streamAddres_ 与 conn_，不能只检查是否有 PLAYSTREAM。

### 5.3 停止通知不等于整条会话都已回收

服务端 `DisConnected → Clear` 会将本连接置 CLOSE、清空自己的 conn_，从关联对象中移除本机码，再向各对端发送 DELETESTREAM，最后移除本机登记。通知中的 streamCount 是**接收方剩余信令关联数**，不是 RTMP 播放连接数。

当前边界还包括：

- `RmoveCustom` 中的 `state_ == IDLE` 只是比较，没有恢复状态，也没有清空对端 conn_。
- 客户端 doDeleteStream 仅在计数为 0 时调用停止回调，没有恢复本地 IDLE。
- 当前客户端没有接通信令 DELETESTREAM 的主动发送流程；关闭播放窗口也不能直接等同于已发送停止请求。
- 服务端能否及时检测断开，以及线程、队列和对象最终能否释放，需要复用关闭检查和实际观察。

信令关联、RTMP Session 和客户端工作线程是三套对象关系，不能凭其中一处清空就判定全部结束。完整关闭分析仍按服务端阶段十一与客户端阶段九进行。

## 6. RTMP：从服务端应答跟回发布方和播放方

### 6.1 命令处理与应答消费

| 动作 | ENET 处理与回复 | 客户端应答消费者 |
| --- | --- | --- |
| 发布连接 connect | `HandleInvoke → HandleConnect` 读取 app，回复 `_result/NetConnection.Connect.Success` | 发布侧 `HandleInvoke → HandleResult`，成功后调用 CretaeStream |
| createStream | `HandleCreateStream` 回复 _result 和分配的 Message Stream ID | HandleResult 保存 stream_id_，再调用 Publish |
| publish | HandleInvoke 取得流名、组合路径；`HandlePublish` 成功时登记发布者，回复 onStatus | `HandleOnStatus` 收到 NetStream.Publish.Start，设置 is_publishing_ |
| 播放方 play | `HandlePlay` 回复 Play.Reset/Play.Start，取得 Session，登记播放连接 | 由 FFmpeg 内部消费；项目随后通过 av_read_frame 取得 Packet |

发布应答的回程从客户端 `OnRead → HandleChunk → HandleMessage → HandleInvoke` 进入，再按 _result 或 onStatus 分派。播放应答不走项目的发布侧 RtmpConnection；AVDEMuxer 在读线程中调用 avformat_open_input，协议交互由 FFmpeg 完成。

发布侧当前主要按状态解释 _result，没有使用事务号关联请求与应答。

发布失败时，服务端可能提交 `NetStream.Publish.BadName/BadConnection`，随后返回 false，进入连接关闭路径。客户端若收到非成功的发布 code，也会返回 false 并关闭连接。当前实现没有等待错误通知发送完成再关闭的保证，因此服务端构造了错误通知，不代表它必然到达客户端，也不代表界面已有错误提示。

### 6.2 用同一实例中的流路径关联发布与播放

例如被控方生成 `rtmp://<地址>:1935/live/2`：

```text
URL → app=live，stream_name=2
  → ENET HandleInvoke 组合 stream_path_="/live/2"
  → 同一 RtmpServer 实例的 GetSession("/live/2")
  → 将发布连接登记为发布者，将播放连接登记为播放器
```

信令服务保存和转交 URL，不代替两条媒体连接。发布和播放必须到达持有同一 Session 的 RTMP 服务实例；不同实例上相同的 /live/2 不会自动汇合。

Message Stream ID 属于各自 RTMP 连接，CSID 用于分块，事务号用于命令交互，FFmpeg stream_index 用于媒体分流；它们都不能替代流路径或信令识别码。进程内递增流名也不保证多台客户端之间唯一。

### 6.3 消息类型决定进入哪个媒体处理函数

| 客户端提交内容 | 线上 RTMP 类型 | ENET 入口与分发 |
| --- | --- | --- |
| AVC 配置、视频编码数据 | 9 | HandleVideo 识别配置或普通数据，交 Session |
| AAC 配置、音频编码数据，按正常音频路径提交时 | 8 | HandleAudio 识别配置或普通数据，交 Session |
| 当前发布器首关键包分支中的 AAC 配置 | **错误地使用 9** | 进入 HandleVideo，不能更新 AAC 配置缓存 |

当前 [RtmpPublisher.cpp](https://github.com/slimesq/ECloudAssistant/blob/main/Pusher/rtmp/RtmpPublisher.cpp) 在首关键包分支把 AVC 和 AAC 配置都交给 SendVideoData。AAC 负载即使以 `AF 00` 开头，也不会让服务端自动转到 HandleAudio；它不满足 AVC 配置条件，会被当作普通视频交给 Session，后续还可能被关键帧门控跳过。

正常分类后，`0x18/0x19` 是项目内部的 AVC/AAC 配置类别。播放连接发送时重新映射为线上视频 9、音频 8，使用自己的 Message Stream ID 和 Chunk 封装。服务端复用编码负载，不进行音视频解码或重新编码。

新播放器的配置补发发生在后续 Session 媒体分发时，AddSink 本身只登记。缓存、首帧门控和复制点直接复用阶段九。

把通过门控的媒体沿完整交接路径接起来：

```text
发布连接 HandleAudio / HandleVideo
  → RtmpSession::SendMediaData
  → 播放连接 SendMediaData
  → SendRtmpChunks → RtmpChunk::CreateChunk → TCP 发送
  → FFmpeg 接收、解析 RTMP 并还原媒体数据
  → AVDEMuxer::FetchStream 中 av_read_frame 取得编码 Packet
  → 按 stream_index 交 h264Decoder_ / aacDecoder_ 的 put_packet 队列
```

Packet 承载的是待解码的编码数据，不是已经解码的 Frame；也不能把一次 TCP 接收、一条 RTMP 消息和一个 Packet 简单画等号。入队之后的解码与输出复用客户端阶段八。

### 6.4 分清已经确认到哪一步

| 结果或标志 | 当前最多说明什么 |
| --- | --- |
| 信令 CREATESTREAM 的成功结果 | 被控客户端启动回调返回成功；实际效果还取决于回调是否按预期绑定 |
| RtmpPublisher::OpenUrl 返回 0 | TCP 已连并提交 C0+C1，尚未等待发布应答 |
| 收到 NetStream.Publish.Start | 服务端接受发布角色；当前 is_publishing_ 未作为媒体发送门槛 |
| 收到 NetStream.Play.Start | 服务端处理了播放请求；GetSession 可新建空会话，不能证明已有发布者或媒体 |
| AVDEMuxer::Open 返回 true | 读线程创建；打开输入和查询流信息在该线程后续执行 |
| 画面、声音实际输出 | 还需要有效配置、媒体、解码、队列和 Qt 输出路径都工作 |

AVDEMuxer 的打开与流信息结果通过 streamCb_ 回调，但当前默认是空操作，AVPlayer 没有绑定这项结果处理。这条回调目前不会将后台打开失败的结果交给 UI 处理。

## 7. 输入：服务端原样转发，最终客户端执行

### 7.1 转发目标来自连接关系

```text
A 的 AVPlayer 输入事件
  → A 的控制信令连接 Send
  → ENET SigConnection::HandleMessage
  → HandleOtherMessage 检查 conn_ 且本连接为 PULLER
  → 将 data->len 个原字节发给 conn_
  → B 的 SigConnection 解包，执行 SendInput 或 QCursor::setPos
```

输入消息体没有另带目标识别码。服务端使用先前建立的 conn_ 决定收件方，因此第 5.2 节的遗漏会影响输入，与 RTMP 是否成功播放是两条检查路径。

| 命令 | 当前客户端总长 | 最终客户端消费 |
| --- | --- | --- |
| MOUSE(10) | 6 字节 | doMouseEvent，解释按下/释放和鼠标按键 |
| MOUSEMOVE(11) | 8 字节 | doMouseMoveEvent，解释拆成四个字节的百分比坐标并定位光标 |
| KEY(12) | 7 字节 | doKeyEvent，解释按下/释放和键值 |
| WHEEL(13) | 5 字节 | doWheelEvent，读取有符号方向并生成滚轮输入 |

服务端当前只按 cmd 分派，HandleOtherMessage 不读取这些输入字段，也不按另一套结构体重新组包。消息长度和分片安全边界继续复用阶段二与阶段七，原样转发不代表已做完协议校验。

### 7.2 声明差异与实际解码问题分别判断

| 项目 | ENET 声明 | 客户端声明 | 当前影响 |
| --- | --- | --- | --- |
| KEY 包头后字段顺序 | key:uint16_t，再 type:uint8_t | type:uint8_t，再 key:uint16_t | 都是 7 字节，偏移不同；服务端当前没有按自己的 Key_body 读取或重建，两个同版本客户端仍按客户端布局解码 |
| WHEEL 字段 | uint8_t | int8_t | 客户端 -1 的字节 FF 原样传到接收端，仍被读为 -1；若服务端按自己的字段解释，才会读成 255 |

所以不能仅凭服务端头文件不同就断言当前透传一定把 KEY/WHEEL 转错。另一方面，客户端 keyReleaseEvent 没有给 type 正确赋值，Qt 键值到 Windows VK 也缺少完整映射，这些直接影响消息生产与执行，应按客户端阶段五定位。

这里能确认的是接口路径。实际坐标是否准确、按键是否释放、输入是否生效，仍需在阶段十二观察。

## 8. 地址核对：找到生产地址的位置

以下是当前源码默认值，用于定位配置来源，不代表你的部署必须使用这些地址，也不代表它们现在可达。

| 地址用途 | 地址生产或使用位置 | 对应监听或消费位置 |
| --- | --- | --- |
| GUI 查询负载 | 客户端 LoginWgt：192.168.31.30:8523 | [LoadBanceServer/main.cpp](../LoadBanceServer/main.cpp)：172.21.205.121:8523 |
| 登录服务上报到负载 | [LoginServer.cpp](../LoginServer/LoginServer.cpp)：连接 172.21.205.121:8523 | LoadBanceSvr；与 GUI 的负载入口分别配置 |

| 返回客户端的信令入口 | LoginConnection 成功分支：172.21.205.121:6539 | [SigServer/main.cpp](../SigServer/main.cpp)；RemoteManager::Init 消费 |
| 媒体入口 | 客户端 doCtreatStream：192.168.31.30:1935/live/递增流名 | [RtmpServer/main.cpp](../RtmpServer/main.cpp)：172.21.205.121:1935；发布者和播放器使用同一 URL |

监听地址与对外通告地址可能因部署映射而不同，应核对实际可达关系。修改监听值不会自动更新资源上报、登录回复或客户端拼出的 URL。

请求 timestamp 使用 Unix 秒，服务端相关超时阈值为 60 秒；客户端连接等待使用毫秒，两者不是同一个超时。对照本次配置时也要核对系统时钟，避免把过期请求误判为地址或布局问题。

编码参数和解码配置来自客户端采编流程，不由 SigSvr 或 RtmpSvr 协商生成。这里只确认它们的生产、发送和缓存入口，不再安排一轮采编配置实验。

## 9. 实际学习步骤

### 第一步：反查登录请求，顺查回复

打开第 3 节的两个服务端处理函数，分别定位 timestamp、code、ip/port 和结果字段。反查 LoginWgt 的生产位置，再指出地址切换和 sig_logined 的消费位置。能解释“请求携带的字段”和“服务端真正使用的字段”有什么区别即可。

### 第二步：跟一次建流，再看两个分支

用第 4.3 节例子跟 JOIN → OBTAINSTREAM → CREATESTREAM → PLAYSTREAM，同时看 code_、objectes_、conn_ 和 URL 在哪里写入。再对照目标不存在与已有流分支，说明哪条回复未被消费、哪项关系没有赋值。

### 第三步：沿同一 URL 跟媒体，沿 conn_ 跟输入

在 RTMP 处理函数中找到 /app/stream_name 和 Session，把发布应答跟回自定义发布客户端，把播放入口跟到 FFmpeg。然后选 KEY 或 MOUSEMOVE，跟一次原字节转发和最终执行，说明媒体路径与输入路径各靠什么关联。

最后按第 8 节核对本次地址。两端阶段十重复覆盖的内容只需对照一次；已有布局推演、媒体观察和关闭结论直接复用，尚未解释的交接点才继续查源码。无需另写探针、搭一套服务或先修完全部缺陷。

静态对应可以在本阶段完成。连接是否可达、当前登录分支的实际响应，以及发布、播放、远程输入和停止结果，按阶段十二的同一轮会话观察。
